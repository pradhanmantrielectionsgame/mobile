# Project Instructions — PradhanMantri Elections Game Mobile

## UI conventions

- Small UTs (Delhi, Chandigarh, Dadra & Nagar Haveli and Daman & Diu, Puducherry, Lakshadweep, Andaman & Nicobar Islands) are never directly tappable on the map — they're too small to hit reliably. Always route their interaction through the existing button-cluster pattern (`union-territories-container` in `index.html`, paired with the timer-pill), not direct map taps. J&K and Ladakh are large enough to tap directly and don't need this treatment.
- **`mobile/` (built 2026-07-23) is the real, playable build** — Booth Ink's markup/CSS wired to a full engine (`mobile/engine.js` pure redistribution/apportionment/starting-position math, `mobile/game.js` phase loop + all systems + AI opponent, `mobile/main.js` DOM glue) per `design/economy-status-map.md`. `design/prototypes/pme-mobile-sheet.html` remains the frozen design-reference prototype it was cloned from (demo-only logic, hardcoded to Modi's 4 agendas) — don't edit game logic there, edit `mobile/*.js`. `index.html`/`styles.css` at repo root is the old desktop-ported skin, superseded by both. Run `npm test` (engine self-check + a full-game simulation) and `npm run serve` (static server, then open `/mobile/index.html`) after changes here.

## Game design principles

- **`docs/wiki.html` is the single authoritative reference for finalized game design** — core loop, win condition, starting position, the redistribution rule, every mechanic category (investment, rally tokens, agendas, regional dominance, special powers), the politician roster, architecture, the AI, and testing. When the question is "how is X supposed to work," check it first. `design/economy-status-map.md` **was** this project's authoritative reference but was formally deprecated 2026-07-29 — it kept drifting out of sync with shipped decisions even while other sections of it were being actively edited (see `docs/wiki.html`'s divergence log, entries 8–11, for concrete examples: it still described the superseded hung-parliament rule and an already-fixed policy tag direction as current). It's kept only as a dated historical decision log now (the tag-cancellation audits, the funds-bump rationale, the seat-apportionment worked example) — `design/plan.md`, `CHANGELOG.md`, and `findings.md` remain dated history in the same sense, not current-state references, and neither is `economy-status-map.md` anymore.
- **`docs/wiki.html` itself needs the same discipline the design doc was held to: don't let it drift.** When a numeric constant or mechanic changes, update the wiki's relevant section in the same session, not "later" — recording the decision in this file is not enough to keep the wiki in sync, exactly the failure mode that got the design doc deprecated in the first place.
- Avoid click-fest mechanics — cap player actions per phase (a fixed number of moves/commitments) rather than allowing unlimited repeated clicking with diminishing returns. Every action should have real opportunity cost against the others available that phase.
- Regional/group dominance bonuses require **every single state** in the group to individually cross 50% popularity — not a seat-weighted average. Confirmed intentional in the desktop app's own logic; treat this as deliberate design, not a bug to loosen.
- For game-economy/balance work (costs, bonuses, decay curves, dominance payouts), reference the **desktop app's real code** (`game-config.js`, `state-info.js`, `campaign-spending.js`, `home-state-bonus.js`, `group-rewards.js`, `state-groups.js`) as ground truth, not mobile's ported version — mobile's economy code is known broken/incomplete in several places (e.g. `checkRegionalDominanceBonuses()` still references retired region fields) and is being actively rewired.
- **Exception, decided 2026-07-21, numbers updated 2026-07-24:** mobile's base economy *scale* (starting funds 5,000, refresh 2,500/phase per player, cost = seats×10) is now independently canonical — it is **not** benchmarked against desktop's numbers (200/200/seats×1) and that comparison is closed, don't reopen it. The 2026-07-24 bump (from 2,500 starting/1,000 refresh) was a direct response to the user's own multi-round playtesting finding insufficient funds to reach a majority win against the AI. This exception is scale only; formula *shapes* (the redistribution rule, the agenda effect formula) still follow desktop's real code as ground truth unless a specific decision says otherwise. See `docs/wiki.html`'s "Money, rallies & agendas" section for the full current formula set and open items.
- **A policy's pull on a region is a per-(policy, region) magnitude, not one shared value for the whole policy** — e.g. National Defense pulls +12 in Eastern Border and −12 in Coastal India, different regions at different (even opposite-sign) strengths for the same policy. `data/policy-tags.json` encodes this directly as `tagEffects: { region: signedMagnitude }` (migrated 2026-07-22 — the old `tier`/`baseMagnitude`/`supportTags`/`opposeTags` shape is gone). Don't reintroduce a policy-wide constant; see `docs/wiki.html`'s "Money, rallies & agendas" section for the current schema and formula.
- **When a state carries several of a policy's tags at once (some supporting, some opposing), sum them into one net value first, then apply that single net through the redistribution engine exactly once — never apply each tag as its own separate transaction.** The 100%-cap and the proportional opponent/Others split are both non-linear per transaction, so sequential opposite-signed transactions don't cancel out the same way a single net value does, even when their magnitudes are equal on paper. See `docs/wiki.html`'s "The map & the 100% rule" section, "net first, apply once."
- **A special power's stated cost must be a genuine resource sacrifice — funds, popularity, or rally tokens — never a timing gate ("usable only in the final phase") or an eligibility condition ("only usable while below national-average popularity").** Both of those cost nothing whenever the power is actually usable, which breaks the "matched cost + benefit" rule for special powers. Two powers shipped with exactly this bug (Tendulkar's National Icon, Hema Malini's Star Power Rally) before being fixed 2026-07-22. **Explicit exception, decided 2026-07-26: Sardar Patel's Iron Unification cannot activate before phase 5** (`requiresMinPhase: 5`, a new engine mechanism in `mobile/game.js`'s `activatePower`/AI `canPay` check), purely for flavor ("mimicking how long real unification took") — a deliberate, acknowledged violation of this rule, not an oversight to "fix" back. **Extended the same day to four more politicians, each with its own real-world timing story**: Narendra Modi's Demonetization (`requiresMinPhase: 3` — the real 2016 shock landed mid-term, not week one), Indira Gandhi's National Emergency (`requiresMinPhase: 5` — the real Emergency came deep into her tenure), B.R. Ambedkar's Constitutional Reform (`requiresMinPhase: 3` — the real Constitution took ~3 years to draft), P.V. Narasimha Rao's Minority Government Survival (`requiresMinPhase: 6` — governing without a majority only means something once one is starting to look out of reach). Don't add further timing-gate costs to other powers without the same explicit call-out.
- **A duration-based special power that lasts "one phase" must set its expiry field to the current `game.phase` at activation, never `game.phase + 1`.** This bans a delayed "triggers at the start of the next phase" pattern for exactly this reason — the effect must self-clear the moment `game.phase` moves past it, which requires it to already be active during the activation phase itself. Modi's Demonetization shipped with this exact off-by-one (`fundsFrozenUntilPhase = game.phase + 1`), letting the AI opponent invest/tap normally for the rest of the phase it was used in before finally freezing the *following* phase — found 2026-07-28 via a diagnostic script directly exercising `investCash`/`tapAgenda`/`aiStep`, fixed to `game.phase`. Check this specifically whenever a new one-phase-duration power is added. **Update 2026-08-21: Modi's Demonetization was deliberately extended to a genuine two-phase duration** (as part of a balance rework — see the agenda/power-rebalance bullet below), which legitimately uses `fundsFrozenUntilPhase = game.phase + 1` again — but paired with `fundsFrozen()` changed from an equality check (`=== game.phase`) to a range check (`game.phase <= pl.fundsFrozenUntilPhase`), so it covers the activation phase *and* the next one, not a delayed single-phase trigger. Don't mistake this for the banned off-by-one pattern reappearing — the distinguishing test is whether the freeze is active immediately upon activation (it is, here) versus only starting the following phase (the banned bug).
- **When a region-tagged policy's seat-equivalent comes out sharply negative, check first whether it's an accidental same-state overlap between that policy's own support and oppose tags** (the same failure pattern as pre-fix National Defense and Hindi Language: a state tagged with both a support region and an unrelated oppose region cancels to zero, silently zeroing out what should be a strong supporter) **before concluding the negativity is deliberate polarization.** Several policies (Land Reforms, Public Sector, Uniform Civil Code, Caste Reservation, Indigenous Rights, Agricultural Reforms, Secularism) haven't had this check yet as of 2026-07-22. **Update 2026-07-26: these seven have now had that overlap check — none showed accidental cancellation, but a *separate*, previously-unperformed check (below) found real problems in three of them.**
- **A policy's `tagEffects` sign and region choice should also be sanity-checked against real-world Indian political geography, as a distinct pass from magnitude balance or same-state-cancellation** — a policy can have internally-consistent, well-balanced numbers that still point the wrong direction thematically. Found via this check 2026-07-26: Public Sector had industrial-vs-agricultural backwards (PSU jobs/union politics are concentrated *in* industrial states, not agricultural ones); National Defense's `CoastalIndia` negative had no real-world story (coastal India has its own major security stake) and was replaced with a lighter `MinorityAreas` penalty; Caste Reservation conflated caste politics with religious-minority politics and omitted South India entirely despite the Dravidian movement's historically strong pro-reservation tradition. Run this check (does the sign/region choice match a real Indian political fault line?) any time a policy's tags are touched, in addition to the existing overlap/magnitude checks above.
- **Popularity/redistribution state should be tracked in integer basis points (bps, 0–10000), never float percentages**, once the redistribution engine is actually implemented in code. Splitting a change between two recipients must round one side and derive the other by subtraction — never round both independently — to guarantee the three shares (yours/opponent's/Others) always sum to exactly 10,000. See `docs/wiki.html`'s "The map & the 100% rule" section for the full worked example.
- **This same "never round independently" discipline extends beyond 2-way splits to any N-way conversion of bps shares into whole units** (e.g. a state's seats, split across P1/P2/Others) — plain `round()` applied to each share separately can over- or under-allocate the total (concrete break: a 3-seat state at 50%/25%/25% independently rounds to 2+1+1 = 4 seats). Use **largest-remainder apportionment** (Hamilton's method: give each share `floor(quota)`, then hand out the leftover units to whichever shares have the largest fractional remainder) instead — it guarantees the parts always sum exactly to the whole. Decided 2026-07-23 for seat conversion specifically; see `docs/wiki.html`'s "The map & the 100% rule" section for the worked example and pseudocode.
- **A greedy per-action scoring formula (cost-efficiency, boost/cost, etc.) must account for remaining headroom/diminishing returns, not just raw cost-efficiency — otherwise it gets stuck endlessly re-targeting an already-maxed option instead of moving on.** Concrete break: `mobile/game.js`'s AI investment scoring (`boost/cost`) always favored the cheapest state in a group regardless of how close that state already was to 100% ownership, so the AI kept dumping funds into an already-maxed state instead of spreading across the group — fixed by scoring on effective remaining headroom (`min(boost, 10000-currentShare)/cost`) instead of raw boost. Found 2026-07-23 while stress-testing the group-based AI investment targeting.
- **That same greedy-scoring discipline has a second, distinct failure mode beyond headroom: a per-Cr or per-token efficiency score must also be normalized by what's actually being bought (e.g. seats), not left as raw %-per-Cr — otherwise it silently favors whichever option is cheapest per attempt regardless of size.** Concrete break: `scoreInvestState`'s `effectiveGain/cost` scored a 1-seat UT at 20–50 and Uttar Pradesh (80 seats) at 0.25–0.6 even on UP's very first, most-boosted tap — cost scales with seat count but the % boost per tap doesn't, so the AI (and a human chasing the same "biggest % shown" intuition) hammered tiny states that often don't even convert to a seat, instead of spreading nationwide the way the design doc's own cost-per-seat invariance claim assumes. Found 2026-07-25; fixed as part of the broader AI investment-targeting rework (see below).
- **Whenever the human interface restricts an action (a batch-only button, a disabled tap target, a UI-level gate), check whether the AI's engine-level code has the same restriction — it usually doesn't by default, since `mobile/game.js`'s AI functions bypass `main.js`'s DOM/button layer entirely and act directly on `game` state.** Concrete break: the human can only invest in 5 of the small UTs (Chandigarh, Dadra & Nagar Haveli/Daman & Diu, Puducherry, Lakshadweep, Andaman & Nicobar) as an all-or-nothing batch via the "Small UTs" button, but `pickAIInvestmentTarget`/`scoreInvestState` treated each as a normal individually-scoreable target — letting the AI cheaply snipe just one (e.g. Puducherry) to deny a regional-dominance group for a fraction of what the human has to spend contesting it back. Found 2026-08-24 from a user report; fixed via `SMALL_UT_BATCH_IDS` forcing the AI into the same batch investment in `aiStep`. Check this pattern any time a new UI-only restriction is added (or a new AI capability gap is reported) — grep the AI's targeting/scoring functions for the same states/scope the restricted UI element covers.
- **Any future change to the AI's own strength or behavior must preserve even, human-comparable real-time pacing — never give it an instant catch-up burst or other advantage a human player can't match at normal play speed.** An early fix for the AI leaving funds unspent by phase end used `G.runAIFull()` right before each phase closed as an instant catch-up burst; the user explicitly rejected this as unfair machine-speed cheating and asked for even pacing throughout the phase instead. AI strength should come from decision quality (what it targets, how it prioritizes), not from acting faster than a human physically can. Decided 2026-07-25 — see `mobile/main.js`'s `planAITickPacing()`.
- **Decided 2026-07-25 (superseding a same-day reversal): the 4 celebrity/non-politician picks (Sachin Tendulkar, Hema Malini, Rajinikanth, Amitabh Bachchan) are deliberately stronger and quirkier than the political roster, not weaker, and not balance-equal to it.** They're explicitly allowed to exceed what a political-roster power does (including Vajpayee's Pokhran Test, previously treated as "the ceiling nothing else reaches" — that no longer holds against this group specifically). Each carries a distinctive mechanic shape (Tendulkar: a 30%-floor `toBps` effect rather than a flat delta; Hema Malini: a stacked nationwide+home bonus; Rajinikanth: an asymmetric dual-region bonus; Bachchan: an "Others"-only source that's high-ceiling but self-limiting). Don't flag one of them out-scaling a political-roster power in the same region (e.g. Rajinikanth vs. Jayalalithaa in South India) as a bug — that's the intended outcome of this decision. **Update 2026-07-28 — clarified scope after a real-money balance pass: "OP" was always meant to describe the special power specifically (these 4, plus the film-persona entry "Sivaji Rao", "don't have the traditional politician appeal thematically"), not the agenda kit riding alongside it.** All 5 had ended up with both a top-tier agenda kit (national avg 13–16, the highest in the roster) *and* a strong/free power stacked together — an unintentional tuning error, not the design intent (Sivaji Rao's One-Day Ordinance in particular had zero cost of any kind while instantly maxing a 48-seat state). Rebalancing these 5 must go through the **special power's cost/timing/magnitude only — never their agenda kit**, which is a deliberate thematic match and shouldn't be touched. (This is also why "No popularity-side downside on any of the four" above no longer holds: Rajinikanth's power now carries a real Hindi Heartland popularity cost, added specifically to bring his win rate down without touching his agenda kit.) Current post-rebalance numbers (`data/politicians-data.json`): Bachchan 6% nationwide / ₹2,000cr / `requiresMinPhase: 6` (down from 12%/₹1,000cr/no gate); Hema Malini 2% nationwide + 14% home bonus (16% total at home, unchanged) / ₹2,500cr (down from 8%/₹500cr); Rajinikanth +22%/+15% (trimmed from +25%/+18% 2026-08-21, after -8% Hindi Heartland alone wasn't enough) and now costs -14% Hindi Heartland (deepened from -8%) / ₹2,000cr (tried ₹3,000cr the same day, reverted once the deepened penalty + magnitude trim alone got win rate down to 59%, no longer an outlier); Sivaji Rao unchanged 100%-home-state effect but now costs all future rally-token income for the rest of the match. Don't reintroduce a funds-cost-only-plus-nerfed-magnitude version of any of these without also checking cost/timing — a magnitude-only lever hits diminishing returns fast (see the balance-sim methodology bullet below). See `docs/wiki.html`'s Special powers section for the current numbers and reasoning.
- **A "steal"-style power must make an explicit, deliberate choice between seize (confiscate — the opponent's resources are destroyed, `seizeFundsPct`/`seizeTokens`) and steal (transfer — the opponent's resources move to the activator, `stealFundsPct`/`stealTokens`), never default to whichever primitive happens to already exist.** Kejriwal's Anti-Corruption Raid, Indira Gandhi's National Emergency, and Sivaji Rao's original One-Day Ordinance were all built on the transfer primitives by default; corrected 2026-07-26 to `seize*` once it was clarified that "raid"/"seizure"/"confiscation" framing means the opponent's resources vanish, not that they move to you. This isn't just wording — it changes the power's real value (see the modeling-methodology bullets above), so re-check the self-cost magnitude whenever switching between the two.
- **A special power that needs to target the exact states in one of the mobile HUD's quick-invest button groups (e.g. `#neBtn`'s Northeast-8) should use the `svgIds` scope in `resolvePowerScope`** (`mobile/game.js`), passing the same explicit svgId list the button itself uses (e.g. `NORTHEAST_IDS`) — not a broader `tags` scope that happens to overlap. Added 2026-08-22 for Mamata Banerjee's State Autonomy Stand: the existing `EasternBorder` tag also covers Bihar/UP/Uttarakhand/HP/West Bengal, well beyond the 8-state Northeast group the power was actually meant to target. `tags` scope remains correct for effects that are genuinely about a `states_data.json` region property rather than mirroring a specific UI button's coverage.
- **A politician can have more than one `homeState`** via the additive `secondaryHomeStates` array in `data/politicians-data.json` — added 2026-07-25 for Kejriwal (`["Punjab"]`, alongside his primary Delhi) because Delhi's 7 Lok Sabha seats made the standard +25% home-state starting bonus far weaker in absolute terms than politicians whose home is a bigger state. Every consumer of `homeState` (`mobile/engine.js`'s starting-position generator, `mobile/game.js`'s `resolvePowerScope` for the `home`/`opponentHome` special-power scopes, `mobile/main.js`'s display line) must read through the `homeStatesOf()`/equivalent helper rather than the raw `homeState` field directly, or a politician with a second home silently loses the bonus in one of the three places. The existing "shared home state nullifies the bonus for both players" rule now applies per overlapping state, not per player — an unrelated second home state isn't nullified just because one of a player's homes happens to collide with the opponent's.
- **When tuning a randomized game mechanic's parameters (e.g. the starting-position generator's advantage-draw thresholds), verify the resulting distribution via direct mean/σ simulation — not inference from percentiles, or intuition about which knob controls what.** Confirmed 2026-07-28 tuning the starting-position generator to a precise target (mean 150 seats, σ~12.5, so ~125/~175 land at ~2σ): several knobs (the baseline population range, the advantage-draw stop threshold, the advantage-draw popularity range) all shift the mean, but only direct measurement showed that raising the advantage-draw stop threshold (`drawStopAt`/`drawBudget` in `mobile/engine.js`) shifts the mean *without* widening σ — the stopping rule is self-correcting (a player who draws a run of small states just needs more draws before crossing the threshold), which keeps σ stable regardless of where the threshold sits. Don't assume from percentile spacing or first-principles reasoning which knob controls spread vs. center — measure it before and after.
- **For politician/agenda balance questions, run `mobile/balance-sim.js`** (`node mobile/balance-sim.js 5`, or higher for more confidence) rather than relying on manual small-sample play — re-run after any politician/agenda tweak. **Read win rate, not avg final seats, as the primary metric.** See `design/testing-and-balance-notes.md` for the full methodology (why AI-vs-AI replaced naive-vs-AI, how hung parliament is scored) and three known methodology traps to avoid when comparing before/after win rates — including a 2026-08-21 finding that this AI-vs-AI harness undervalues conditional/exploit-dependent powers relative to unconditional/guaranteed ones (confirmed on Modi's Demonetization).
- **Hung parliament is always a draw** (`mobile/game.js`'s `finalizeGame()`, ADR-0010 — supersedes ADR-0006, which gave the AI a tie-break advantage on the assumption ties would be rare). Revised 2026-07-28 once the balance-sim measurements above showed hung parliament actually occurs in 48–98% of games per politician — with the roster tuned to be harder to win outright, defaulting every undecided match to an AI win would make "the AI silently wins" the modal outcome, not a rare edge case. **When changing what a `game.winner`/game-state outcome means, grep for every place that independently re-derives the same conclusion, not just where `game.winner` is read** — `mobile/main.js`'s `showEndOverlay()` had its own separate `game.players.p2.isAI` check driving the end-screen headline that would have kept showing "you lose" even after `finalizeGame()` was fixed, since it never actually consulted `game.winner` for this branch. This project has hit this "two places must agree" failure mode before (agenda effect text vs. real benefits/costs, the `[hidden]` CSS attribute rule) — treat it as a standing checklist item whenever a game-outcome rule changes.

- **The politician-unlock progression (added 2026-08-24, local-only, `localStorage`) is deliberately client-side-enforced and bypassable — a player who edits `localStorage` or the DOM via devtools can unlock everything instantly, and that's accepted, not a bug to fix.** This is single-player-vs-AI with no leaderboard or real-money stake, so a bypass only "cheats" the player themselves; real enforcement would require a server-authoritative account/backend, the same tier of work already deferred for multiplayer (see Architecture constraints below). Don't propose obfuscating/hardening the client-side check — that can't actually close the hole (any client-side gate is editable by definition) and isn't worth the effort until real accounts exist. See `mobile/main.js`'s `loadUnlockedPoliticians`/`unlockPolitician`/`isPoliticianUnlocked`.

## Architecture constraints

- Do not rewrite this game in React Native or Flutter for iOS/Android app store distribution. The UI is DOM/CSS/SVG-heavy (interactive map, CSS animations) and the game itself is turn/phase-based with no native-performance requirement, so a native-framework rewrite buys nothing. Wrap the existing vanilla HTML/CSS/JS with Capacitor instead — it carries the current UI over almost unchanged.

## Data & config conventions

- Prefer config/data files (JSON under `data/`) over hardcoding values in JS — politician rosters, state groupings, policy tags, token/economy constants, etc. belong in JSON, not embedded in engine code. Keeps experimentation (tuning a bonus value, rebalancing a group, adding a politician) a data edit instead of a code change, and matches this project's existing single-source-of-truth pattern (`game-config.json` driving `config-manager.js`).
- **Don't mint a new agenda tag for just one politician — a new tag needs 2+ real, distinct politician-biography fits before it clears the bar for creation.** Confirmed as a standing preference 2026-08-21 after coming up repeatedly in the same session: `Judicial Activism` was retired specifically because it only had one real (and shaky) fit, repurposed into `Administrative Reform` once it also fit Sardar Patel; a proposed "Farmers' Issues" tag (Rahul Gandhi's NYAY/farm-loan-waiver angle) was declined because existing `Agricultural Reforms` was judged broad enough to already cover that ground; a proposed "Local Self-Governance" tag (Rajiv Gandhi's Panchayati Raj push) was declined for having no second real candidate. If a politician's kit has a weak/generic slot and no existing pool tag fits well, prefer leaving the generic slot over minting a single-use tag — see the growing pool at 32 entries as of 2026-08-21 in the bullet below for what's already available.
- Politicians draw their agendas from a **shared pool** (`data/policy-tags.json`, 32 entries as of 2026-08-21, all reachable — `Privatization` was orphaned until 2026-07-22, now assigned to Vajpayee) — each politician's `policies` array just lists 4 names from that pool, plus 1 unique special power. Multiple politicians can and do share the same agenda (e.g. National Defense). Don't build a per-politician bespoke agenda table. An agenda becomes "exclusive" simply by only one politician's list referencing it — no explicit exclusivity flag needed.
- **2026-08-21 — agenda-pack thematic-distinctiveness pass: 7 new tags added, `Judicial Activism` retired, 12 of 21 politicians' kits touched, all grounded in real biography, not invented for balance alone.** Trigger: overlap analysis found 6 politician pairs sharing 3 of their 4 agendas (worst: Mamata Banerjee/Jayalalithaa/Hema Malini all carried the identical flat-nationwide pair {Women's Empowerment, Healthcare}), plus 4 real region tags (`CoastalIndia`, `TravelAndTourism`, `Pilgrimage`, `NationalParksWildlife` in `states_data.json`) that almost no policy used. New tags: **Coastal Economy** (Mamata Banerjee — Bengal coast/Sundarbans; Rajinikanth — has publicly advocated for Tamil Nadu fishermen), **Food Security** (Manmohan Singh — National Food Security Act 2013; Jayalalithaa — Amma Canteens), **Heritage and Tourism** (Amitabh Bachchan — the "Incredible India" campaign face; Hema Malini — Mathura MP, pushed Braj tourist-corridor development), **Environmental Conservation** (Indira Gandhi — launched Project Tiger 1973; Hema Malini — Yamuna river cleanup advocacy in her Mathura constituency), **Sports and Entertainment** (Sachin Tendulkar; Rajinikanth), **Nationalization** (Indira Gandhi — bank/coal/insurance nationalization 1969-73; mirrors `Privatization` as an opposite-pole pair), **Foreign Policy & Diplomacy** (P.V. Narasimha Rao — Look East Policy; flat nationwide bonus, no natural regional signature — considered and rejected for Nehru, since his existing Infrastructure (Bhakra Nangal) and Public Sector are both already legitimate real fits and he doesn't need a 5th real thing forced into a 4-slot kit). `Judicial Activism` was retired and repurposed into **Administrative Reform** (Education +8/IndustrialCorridor +6/Manufacturing +6/TribalLands −4/AgriculturalRegion −4) — it had no real signature fit for anyone but Ambedkar (and even that's a stretch: "judicial activism" describes what courts do *after* a constitution exists, not the drafting of one), and the project's own no-one-off-tags preference meant it only cleared the bar for creation once repurposed to also fit Sardar Patel (founder of the modern IAS). **Every new tag was run through the existing same-state-cancellation check** (`states_data.json`) before shipping — two drafts failed and were adjusted before finalizing: `Environmental Conservation`'s first draft cancelled to exactly zero in Jharkhand (TribalLands +6 vs IndustrialCorridor −6, bumped TribalLands to +8), and `Nationalization`'s first draft cancelled to zero in Tamil Nadu/West Bengal (Manufacturing +6 vs CoastalIndia −6, bumped Manufacturing to +8). Full per-politician rationale and the 21-politician overlap audit lives in the conversation this decision came from — `docs/wiki.html`'s "Money, rallies & agendas" and "Politicians & agendas" sections carry the current summary.
- No CRUD script/tool wanted for managing `politicians-data.json`/`policy-tags.json` — edits happen via direct natural-language requests to Claude (e.g. "add a politician profile for X", "change Hindutva's tier"), not a CLI or admin UI. `check_data_consistency.js` is the validation safety net; run it after any edit.
- The legacy desktop reader (`js/config-manager.js`, `js/data-loader.js`) reads `game-config.json`/`politicians-data.json` via hardcoded key names with no fallback defaults (e.g. `config.investmentSystem.baseCostPerSeat`) — a renamed/missing key doesn't throw, it silently propagates `undefined`/`NaN` into that build's economy. Any future schema change to these two files must preserve those exact legacy key names, or explicitly accept (and document) breaking that already-deprecated build — this is why `mobile/`'s new constants live in `game-config.json`'s additive `mobileEconomy` namespace instead of restructuring the existing keys.
- `data/policy-tags.json`'s real content is under a `policyTags` top-level key (not the file root); `data/politicians-data.json`'s is under `politicians`; `data/states_data.json` has a leading UTF-8 BOM that breaks `JSON.parse` on a raw `fs.readFileSync`. Browser `fetch().json()` tolerates all of this transparently, which is why it can go unnoticed — any script reading these files directly via Node (tests, one-off inspection) must strip a possible leading BOM and unwrap the named key first (see `mobile/game.js`'s `stripBOM()`/`normalizeGameData()` for the reference implementation).
- **`mobile/engine.js` has no `module.exports` — it assigns `root.PMEEngine = {...}` onto `window`/`global` inside a UMD-style wrapper, matching the plain-`<script>`-tag convention the rest of the browser code uses.** A Node script that `require()`s it directly gets back `{}`; the functions live at `global.PMEEngine` instead (the require still runs the file for its side effect, including its own `node mobile/engine.js` self-check block if invoked as the entry module). `mobile/game.js`/`mobile/simulate.js` already route around this correctly by not needing direct `E.*` access from outside — any future one-off Node script that does need `E.investmentBoostBps`/`E.gainAt`/etc. directly must `require(path)` then read `global.PMEEngine`, not destructure the `require()` return value. Confirmed 2026-08-22 writing a standalone verification script outside the existing test harness.

## Frontend technical rules

- **Never set `touch-action:manipulation` in `mobile/index.html` — it still permits pinch-zoom** (the spec value only blocks double-tap-to-zoom, pinch-zoom stays enabled under `manipulation`). Confirmed 2026-08-24 after the user reported the app randomly zooming out during fast two-thumb play — the global `*{touch-action:manipulation}` rule was the cause. Fixed to `touch-action:pan-x pan-y`, which blocks pinch-zoom too while still permitting the app's two genuine native-scroll spots (politician-select carousel swipe, share-sheet horizontal scroll). Do not "fix" this by adding a `<meta name="viewport">` tag instead — that breaks the app's entire no-viewport-tag auto-zoom-out rendering convention (see the 2.5x-authored-scale bullet below) that most of the UI's sizing depends on.
- Never rely on CSS Grid shrink-to-fit with `1fr` tracks when a declared pixel/icon size needs to actually hold — the grid container's width goes undefined and the browser silently overrides the item's declared size to fit an accidental viewport computation. Give the grid container an explicit, screen-relative width (e.g. `min(calc(100% - Npx), cap)`) instead. This already caused a real, hard-to-spot sizing bug in a mobile prototype's icon grid.
- Every standalone HTML file (prototype or real game) must declare `<meta charset="UTF-8">` as the very first tag. Claude's Artifact hosting sets the correct charset header automatically, but any other host (a local dev server, GitHub Pages, etc.) may not — without the explicit tag, every emoji, the ₹ symbol, and em dashes render as mojibake.
- When sizing mobile UI chrome (buttons, text, icons) in a prototype meant to represent real device proportions, calibrate against the actual iPhone 14 viewport (390×844, this project's default target) — not against how it looks inside the Claude Artifact viewer. The Artifact viewer wraps pages in its own ~150–200px title-bar chrome, which makes a `flex:1` map region look shorter than it will on a real device, and everything sized to "look right" against that preview reads as too small once viewed full-screen.
- A collapsible tray/panel (`max-height:0; overflow:hidden` to hide, animated open) still occupies its full declared *width* as a flex sibling even while collapsed to zero height — this silently inflates the gap between adjacent elements in the same flex row. Take it out of normal flow with `position:absolute` (anchored to a `position:relative` wrapper around just its own toggle button) instead of relying on collapsed height alone to make it width-neutral.
- For alternating-row hex/brick (honeycomb) layouts, give neighboring rows differing item counts (N, N−1) and center each row independently (`justify-content:center`) — no manual horizontal offset/margin needed. An N-item row and an (N−1)-item row, both centered on the same container width, differ by exactly half a hex+gap pitch, which is the correct honeycomb interlock offset for free.
- Safari-specific mobile bugs (viewport meta behavior, safe-area-insets, dynamic toolbar) must be verified with Playwright's `webkit` engine + an iPhone device profile (`devices['iPhone 14']`), not Chromium — Chromium ignores the page's own `<meta viewport>` tag even with an explicit viewport size set, so it cannot reproduce this whole class of bug.
- Playwright's `devices['iPhone 14']` preset sets `viewport: {width:390, height:664}`, not 844 — 844 is only the preset's `screen` field (the physical panel), modeling real Safari's chrome-reduced usable content area. Judge whether Booth Ink's ~755–765px fixed chrome will fit against 664px, not 844px, when reasoning from a Playwright screenshot — and treat a real device or Capacitor-wrapped build as the final check regardless, since headless webkit still isn't a perfect stand-in for Safari on this specific viewport-fallback behavior.
- Booth Ink (`pme-mobile-sheet.html`) intentionally has no `<meta name="viewport">` tag — its fixed-height chrome (header + news ticker + groups bar + info panel, ~755–765px) doesn't fit within a true 390×844 device-width viewport in a plain Safari tab, only within Safari's fallback ~980px virtual-canvas mode that a missing viewport tag triggers. Don't add a viewport meta tag here without first trimming chrome density, or confirming standalone/home-screen-installed mode is the actual deployment target.
- Booth Ink's map SVG renders 3 states (Uttarakhand `INUT`, Ladakh `INLA`, Himachal Pradesh `INHP`) as a duplicate-ID `<circle>` overlay layered on top of their real `<path>` boundary. Any map interaction code (paint, click, highlight) must query `path[id], circle[id]` together — targeting `path[id]` alone silently breaks these three states.
- Use `fill-opacity` (not `opacity`) to dim SVG map states — plain `opacity` fades the stroke/border along with the fill, which can make a dimmed state's outline disappear entirely.
- **Any element toggled via the `hidden` attribute needs an explicit `<selector>[hidden]{display:none}` rule if that same selector's base class already sets its own `display` value** — author CSS beats the browser's default `[hidden]{display:none}` UA-stylesheet rule at equal specificity, so `el.hidden = true` silently does nothing without it. Confirmed 4 times in this codebase now (`.overlay`, `.group-readout`, `.target-banner`, `.vs-bar`) — treat it as a checklist item whenever a new toggleable block gets its own `display` (flex/grid/etc.) in its base rule.
- **A decorative flex item with no intrinsic content (an empty-span color stripe, a bare spacer div) needs an explicit `width:100%` — it silently collapses to zero width whenever its flex-container parent's `align-items` isn't the default `stretch`.** The same `.tricolor` rule rendered correctly on the select-screen ballot card (parent has no `align-items` override) and was completely invisible (0×0 bounding rect) on the end-of-game card (parent sets `align-items:center` to center the seal/headline). Found 2026-07-24 — don't assume a rule ported from one flex context behaves the same in a sibling one with different alignment.
- **Any UI in `mobile/index.html` must be authored at ~2.5x the visually-intended font/padding/gap/icon size, not real-world size.** This app has no `<meta viewport>` tag (see the Local dev bullet below on why), so WebKit/Chromium both render it on a virtual ~980px-wide canvas and zoom the whole page out ~0.4x to fit the real device (`window.visualViewport.scale` measures 0.398–0.401). The in-game HUD (`.phase-chip`, `.iconbtn`, `.action-btn`, etc.) is already authored this way — e.g. a 35px phase-chip font renders at a normal ~14px real size. The politician-select/end-game ballot-card CSS was originally authored at literal real-world sizes instead (19px name, 13px body text), so it rendered at ~40% of intended size — reported as "text too small and unreadable," fixed 2026-07-24 by scaling every font-size/padding/margin/gap/icon-size in that CSS up ~2.5x. **Exception: leave border-width, box-shadow offsets, and `:active` press-transform values unscaled** — confirmed those are always authored small (1–3px) everywhere in this codebase regardless of whether the rest of a rule is scaled (ballot-card's `border:3px solid` and in-game `.iconbtn`'s identical `border:3px solid` render at the same real thickness on purpose). **Not a one-time pass — confirmed 2026-07-27 that the settings overlay (`.settings-row`/`.settings-help`, 15px/13px) was still at real-world scale years after the convention was established elsewhere**, reported as "small font... ton of whitespace" (the unscaled padding/gaps left the overlay looking sparse too). Don't assume an earlier scale-up pass caught every region of `mobile/index.html` — check the actual `font-size` declarations for any UI area about to be touched.
- **iOS Safari blocks `.play()` on an `<audio>` element until that specific element has been played from within a real user gesture at least once — per-element, not per-page.** Confirmed 2026-07-27 debugging a report that the end-game sound wasn't playing: `game_over`, `cash_added`, and `phase_reset` are only ever triggered from a `setInterval` callback (`doEndPhase`), never a tap, so all three were silently blocked on strict mobile browsers while gesture-triggered sounds (agenda taps, rally deploys, special-power activation) worked fine. Fixed via `unlockSounds()` (`mobile/main.js`), which plays-then-pauses every `Audio` element inside the welcome screen's "Begin Campaign" click handler — the first real gesture in the app. Any future sound that only ever fires from a non-gesture context (a timer, an AI turn) must be added to that same unlock pass or it will silently never play on iOS.
- **Any fallback/alternate sound path must preserve whatever ducking state is already active, not reset volume before playing the fallback.** `playPowerSound()` (`mobile/main.js`) ducks `bg_music` to 0 before playing a politician's dedicated power-sound clip; its original `.catch()` fallback (for the 14/20 politicians without a dedicated file) restored `bg_music` to full volume *before* playing the generic `fanfare` sound — undoing the duck right when the fallback needed it most, so fanfare played over full-volume music. Found 2026-07-28 from a user report of power-sound audio "drowned out by background music." Fixed by keeping the duck applied through the fallback too, restoring only once whichever sound (dedicated or fanfare) actually finishes. Also added a shared Web Audio `GainNode` (2.5x) on power-sound playback since `HTMLAudioElement.volume` caps at 1.0 and some clips (e.g. `Rajinikanth.mp3`) are mastered too quietly to hear even with music fully ducked.
- **A new fixed-position UI element in `mobile/index.html` must be checked against `.ut-bar` and `.pol-footer`'s Play button before assuming the screen's corners/bottom edge are free.** `.ut-bar` (the stage HUD) spans the full width at `bottom:14px` — small-UT invest buttons already occupy that entire strip, corners included. `.pol-footer`'s "Play as X" button sits at the bottom of each scrollable ballot card on the select screen — its exact on-screen position depends on card scroll/content height, so it can't be assumed clear either. Confirmed 2026-08-22 building the tutorial's persistent Back/Next controls: an initial viewport-fixed bottom-corner design would have sat directly on top of both. Fixed by docking those buttons in-flow within whichever card/banner is actually showing (JS-relocated single button pair via `appendChild`) instead of `position:fixed`.
- **iOS Safari's Intelligent Tracking Prevention caps all script-writable storage (`localStorage`, Cache API) to ~7 days of inactivity for a site that isn't installed to the home screen** — a plain bookmark/tab is subject to this purge, standalone (Add to Home Screen) mode is exempt. Relevant to both the service-worker offline cache and any `localStorage`-based feature (e.g. the politician-unlock progression) — there's no code-side fix, only prompting users toward Add to Home Screen for reliability. Noted 2026-08-24 while building/discussing both of those features.

## Deployment

- **The `origin` remote (`pradhanmantrielectionsgame.github.io`) is a live GitHub Pages site with no build workflow — it serves whatever is on `main`'s root directly, no staging step.** Confirmed 2026-07-27: `mobile-ui-overhaul` was 72 commits ahead of `main` with 0 commits behind (a clean fast-forward available), but `git diff main mobile-ui-overhaul --stat` on root-level paths showed `index.html` and all 45 files under `js/` had diverged substantially (many deleted, replaced with new implementations) — not just `mobile/` being added alongside the old desktop game. Merging would have silently overwritten the live desktop game at the root URL, not added the mobile build next to it at `/mobile/`. Before ever merging a long-lived feature branch into `main` on this repo, check root-level file diffs — not just the ahead/behind commit count — and treat any push to `main` as a real public deploy, not a backup. (For remote phone-testing without touching Pages/`main` at all, a temporary tunnel — e.g. `cloudflared tunnel --url http://localhost:8934` — pointed at the local `npm run serve` works and needs no GitHub interaction.)
