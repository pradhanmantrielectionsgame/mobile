# Project Instructions — PradhanMantri Elections Game Mobile

## UI conventions

- Small UTs (Delhi, Chandigarh, Dadra & Nagar Haveli and Daman & Diu, Puducherry, Lakshadweep, Andaman & Nicobar Islands) are never directly tappable on the map — they're too small to hit reliably. Always route their interaction through the existing button-cluster pattern (`union-territories-container` in `index.html`, paired with the timer-pill), not direct map taps. J&K and Ladakh are large enough to tap directly and don't need this treatment.
- **`mobile/` (built 2026-07-23) is the real, playable build** — Booth Ink's markup/CSS wired to a full engine (`mobile/engine.js` pure redistribution/apportionment/starting-position math, `mobile/game.js` phase loop + all systems + AI opponent, `mobile/main.js` DOM glue) per `design/economy-status-map.md`. `design/prototypes/pme-mobile-sheet.html` remains the frozen design-reference prototype it was cloned from (demo-only logic, hardcoded to Modi's 4 agendas) — don't edit game logic there, edit `mobile/*.js`. `index.html`/`styles.css` at repo root is the old desktop-ported skin, superseded by both. Run `npm test` (engine self-check + a full-game simulation) and `npm run serve` (static server, then open `/mobile/index.html`) after changes here.
- The mobile build is single-player-vs-AI only — live human matchmaking (ADR-0001/0002) needs a Firebase/Supabase backend, an external service account the user hasn't asked to stand up, so it's out of scope until requested. The AI (`mobile/game.js` `runAI`) is a greedy heuristic, not adversarially tuned.
- 13 of 20 politicians' special-power numbers (`data/politicians-data.json` → `power` field) are a first-pass concrete assignment following the same conventions as the 6 the design doc explicitly reworked — not a substitute for a real balance/playtesting pass, which the design doc itself still marks open. 11 of 20 politician portrait images (`assets/images/*.png`) don't exist; the select screen falls back to a colored initial circle.
- **The politician-select carousel and end-of-game results screen use a "ballot card" visual identity — Booth Ink's own light-theme ink/brass/stamp/paper materials (tricolor stripe, brass-ringed seal, ticket-stub die-cut, decree box), not a literal Pokémon-style holo-foil card and not a dark theme.** Approved mockup and rationale: `design/prototypes/pol-card-mockup.html`. The app has no dark mode anywhere else, so this screen shouldn't invent one either — confirmed 2026-07-24 after a first dark-card-stock draft was rejected specifically for clashing with the rest of the app's light theme.
- **Don't reintroduce raw per-politician agenda bonus numbers (`data/politicians-data.json`'s `policies[].bonus`) in the select-screen UI.** They were deliberately removed 2026-07-24 as meaningless after the agenda-effect-system revamp; the replacement is a tap-to-expand region-effect breakdown (`agendaEffectChips()` in `mobile/main.js`, shared with the in-game agenda-info panel) reading real `policy-tags.json` data instead.
- **The app's real entry point is now a separate full-bleed welcome screen (`#welcomeOverlay` in `mobile/index.html`), not the politician-select screen.** Added 2026-07-25, reusing `assets/images/PradhanMantriBg.png` (an older poster-collage illustration, stylistically distinct from the rest of Booth Ink's flat-vector look) as a full-bleed `object-fit:contain` background with a dark scrim, a "Begin Campaign" button that hides `#welcomeOverlay` and reveals `#selectOverlay` (`mobile/main.js`). The select screen's own `<h1>` header is unchanged and still renders once revealed.

## Game design principles

- **`design/economy-status-map.md` is the single authoritative reference for finalized game design** — core loop, win condition, starting position, the redistribution rule, every mechanic category (investment, rally tokens, agendas, regional dominance, special powers), the politician roster, and plausibility numbers. When the question is "how is X supposed to work," check it first, before `design/plan.md`, `CHANGELOG.md`, or `findings.md` — those remain the dated history behind the decisions, not the reference for their current state.
- **That document's "Known bugs"/"Still open" lists can lag real code state significantly — verify against actual code and tests before implementing a fix for any reported bug, don't take the list at face value.** Confirmed 2026-07-23: 5 of 13 items pulled directly from that section (AI fund-spend, a starting-position seat blowup, agenda per-tap proration, hung-parliament resolution, seat-apportionment rounding) turned out already fixed in `mobile/engine.js`/`mobile/game.js` by the time they were checked — a targeted diagnostic script or stress test against the actual code caught this before any wasted reimplementation.
- **The reverse direction of the rule above also holds: when a numeric constant in `data/game-config.json` (or similar) changes, check whether `design/economy-status-map.md`'s own prose needs updating too — recording the decision here in CLAUDE.md is not enough to keep the design doc in sync.** Confirmed 2026-07-24: the 2026-07-24 funds bump (exception noted below) was recorded in this file and live in `game-config.json` for a full day before the design doc's Core loop, Agenda, and Plausibility-check sections were updated to match — found and fixed during a full documentation-wiki pass (`docs/wiki.html`) that cross-referenced the design doc against actual code/config rather than trusting its stated numbers.
- Avoid click-fest mechanics — cap player actions per phase (a fixed number of moves/commitments) rather than allowing unlimited repeated clicking with diminishing returns. Every action should have real opportunity cost against the others available that phase.
- Regional/group dominance bonuses require **every single state** in the group to individually cross 50% popularity — not a seat-weighted average. Confirmed intentional in the desktop app's own logic; treat this as deliberate design, not a bug to loosen.
- For game-economy/balance work (costs, bonuses, decay curves, dominance payouts), reference the **desktop app's real code** (`game-config.js`, `state-info.js`, `campaign-spending.js`, `home-state-bonus.js`, `group-rewards.js`, `state-groups.js`) as ground truth, not mobile's ported version — mobile's economy code is known broken/incomplete in several places (e.g. `checkRegionalDominanceBonuses()` still references retired region fields) and is being actively rewired.
- **Exception, decided 2026-07-21, numbers updated 2026-07-24:** mobile's base economy *scale* (starting funds 5,000, refresh 2,500/phase per player, cost = seats×10) is now independently canonical — it is **not** benchmarked against desktop's numbers (200/200/seats×1) and that comparison is closed, don't reopen it. The 2026-07-24 bump (from 2,500 starting/1,000 refresh) was a direct response to the user's own multi-round playtesting finding insufficient funds to reach a majority win against the AI. This exception is scale only; formula *shapes* (the redistribution rule, the agenda effect formula) still follow desktop's real code as ground truth unless a specific decision says otherwise. See `design/economy-status-map.md` for the full current formula set and open items.
- **A policy's pull on a region is a per-(policy, region) magnitude, not one shared value for the whole policy** — e.g. National Defense pulls +12 in Eastern Border and −12 in Coastal India, different regions at different (even opposite-sign) strengths for the same policy. `data/policy-tags.json` encodes this directly as `tagEffects: { region: signedMagnitude }` (migrated 2026-07-22 — the old `tier`/`baseMagnitude`/`supportTags`/`opposeTags` shape is gone). Don't reintroduce a policy-wide constant; see `design/economy-status-map.md`'s Agenda section for the current schema and formula.
- **When a state carries several of a policy's tags at once (some supporting, some opposing), sum them into one net value first, then apply that single net through the redistribution engine exactly once — never apply each tag as its own separate transaction.** The 100%-cap and the proportional opponent/Others split are both non-linear per transaction, so sequential opposite-signed transactions don't cancel out the same way a single net value does, even when their magnitudes are equal on paper. See `design/economy-status-map.md`'s `#pot` section, "net first, apply once."
- **A special power's stated cost must be a genuine resource sacrifice — funds, popularity, or rally tokens — never a timing gate ("usable only in the final phase") or an eligibility condition ("only usable while below national-average popularity").** Both of those cost nothing whenever the power is actually usable, which breaks the "matched cost + benefit" rule for special powers. Two powers shipped with exactly this bug (Tendulkar's National Icon, Hema Malini's Star Power Rally) before being fixed 2026-07-22.
- **When a region-tagged policy's seat-equivalent comes out sharply negative, check first whether it's an accidental same-state overlap between that policy's own support and oppose tags** (the same failure pattern as pre-fix National Defense and Hindi Language: a state tagged with both a support region and an unrelated oppose region cancels to zero, silently zeroing out what should be a strong supporter) **before concluding the negativity is deliberate polarization.** Several policies (Land Reforms, Public Sector, Uniform Civil Code, Caste Reservation, Indigenous Rights, Agricultural Reforms, Secularism) haven't had this check yet as of 2026-07-22.
- **Popularity/redistribution state should be tracked in integer basis points (bps, 0–10000), never float percentages**, once the redistribution engine is actually implemented in code. Splitting a change between two recipients must round one side and derive the other by subtraction — never round both independently — to guarantee the three shares (yours/opponent's/Others) always sum to exactly 10,000. See `design/economy-status-map.md`'s redistribution-rule section for the full worked example.
- **This same "never round independently" discipline extends beyond 2-way splits to any N-way conversion of bps shares into whole units** (e.g. a state's seats, split across P1/P2/Others) — plain `round()` applied to each share separately can over- or under-allocate the total (concrete break: a 3-seat state at 50%/25%/25% independently rounds to 2+1+1 = 4 seats). Use **largest-remainder apportionment** (Hamilton's method: give each share `floor(quota)`, then hand out the leftover units to whichever shares have the largest fractional remainder) instead — it guarantees the parts always sum exactly to the whole. Decided 2026-07-23 for seat conversion specifically; see `design/economy-status-map.md`'s Core loop section for the worked example and pseudocode.
- **A greedy per-action scoring formula (cost-efficiency, boost/cost, etc.) must account for remaining headroom/diminishing returns, not just raw cost-efficiency — otherwise it gets stuck endlessly re-targeting an already-maxed option instead of moving on.** Concrete break: `mobile/game.js`'s AI investment scoring (`boost/cost`) always favored the cheapest state in a group regardless of how close that state already was to 100% ownership, so the AI kept dumping funds into an already-maxed state instead of spreading across the group — fixed by scoring on effective remaining headroom (`min(boost, 10000-currentShare)/cost`) instead of raw boost. Found 2026-07-23 while stress-testing the group-based AI investment targeting.
- **That same greedy-scoring discipline has a second, distinct failure mode beyond headroom: a per-Cr or per-token efficiency score must also be normalized by what's actually being bought (e.g. seats), not left as raw %-per-Cr — otherwise it silently favors whichever option is cheapest per attempt regardless of size.** Concrete break: `scoreInvestState`'s `effectiveGain/cost` scored a 1-seat UT at 20–50 and Uttar Pradesh (80 seats) at 0.25–0.6 even on UP's very first, most-boosted tap — cost scales with seat count but the % boost per tap doesn't, so the AI (and a human chasing the same "biggest % shown" intuition) hammered tiny states that often don't even convert to a seat, instead of spreading nationwide the way the design doc's own cost-per-seat invariance claim assumes. Found 2026-07-25; fixed as part of the broader AI investment-targeting rework (see below).
- **Any future change to the AI's own strength or behavior must preserve even, human-comparable real-time pacing — never give it an instant catch-up burst or other advantage a human player can't match at normal play speed.** An early fix for the AI leaving funds unspent by phase end used `G.runAIFull()` right before each phase closed as an instant catch-up burst; the user explicitly rejected this as unfair machine-speed cheating and asked for even pacing throughout the phase instead. AI strength should come from decision quality (what it targets, how it prioritizes), not from acting faster than a human physically can. Decided 2026-07-25 — see `mobile/main.js`'s `planAITickPacing()`.

## Architecture constraints

- Do not rewrite this game in React Native or Flutter for iOS/Android app store distribution. The UI is DOM/CSS/SVG-heavy (interactive map, CSS animations) and the game itself is turn/phase-based with no native-performance requirement, so a native-framework rewrite buys nothing. Wrap the existing vanilla HTML/CSS/JS with Capacitor instead — it carries the current UI over almost unchanged.

## Data & config conventions

- Prefer config/data files (JSON under `data/`) over hardcoding values in JS — politician rosters, state groupings, policy tags, token/economy constants, etc. belong in JSON, not embedded in engine code. Keeps experimentation (tuning a bonus value, rebalancing a group, adding a politician) a data edit instead of a code change, and matches this project's existing single-source-of-truth pattern (`game-config.json` driving `config-manager.js`).
- Politicians draw their agendas from a **shared pool** (`data/policy-tags.json`, 24 entries, all 24 reachable — `Privatization` was orphaned until 2026-07-22, now assigned to Vajpayee) — each politician's `policies` array just lists 4 names from that pool, plus 1 unique special power. Multiple politicians can and do share the same agenda (e.g. National Defense). Don't build a per-politician bespoke agenda table. An agenda becomes "exclusive" simply by only one politician's list referencing it — no explicit exclusivity flag needed.
- No CRUD script/tool wanted for managing `politicians-data.json`/`policy-tags.json` — edits happen via direct natural-language requests to Claude (e.g. "add a politician profile for X", "change Hindutva's tier"), not a CLI or admin UI. `check_data_consistency.js` is the validation safety net; run it after any edit.
- The legacy desktop reader (`js/config-manager.js`, `js/data-loader.js`) reads `game-config.json`/`politicians-data.json` via hardcoded key names with no fallback defaults (e.g. `config.investmentSystem.baseCostPerSeat`) — a renamed/missing key doesn't throw, it silently propagates `undefined`/`NaN` into that build's economy. Any future schema change to these two files must preserve those exact legacy key names, or explicitly accept (and document) breaking that already-deprecated build — this is why `mobile/`'s new constants live in `game-config.json`'s additive `mobileEconomy` namespace instead of restructuring the existing keys.
- `data/policy-tags.json`'s real content is under a `policyTags` top-level key (not the file root); `data/politicians-data.json`'s is under `politicians`; `data/states_data.json` has a leading UTF-8 BOM that breaks `JSON.parse` on a raw `fs.readFileSync`. Browser `fetch().json()` tolerates all of this transparently, which is why it can go unnoticed — any script reading these files directly via Node (tests, one-off inspection) must strip a possible leading BOM and unwrap the named key first (see `mobile/game.js`'s `stripBOM()`/`normalizeGameData()` for the reference implementation).

## Local development & testing

- On this machine, phone-testing the local dev server (`npm run serve`, port 8934) over LAN needs the Wi-Fi network's Windows category set to **Private**, not just a firewall port-allow rule — a port rule alone was confirmed insufficient while the network stayed classified Public (`Set-NetConnectionProfile -InterfaceAlias "Wi-Fi" -NetworkCategory Private`, run elevated). Check/set this first before troubleshooting further if a phone can't reach the local server.
- `mobile/index.html` cannot be published as a self-contained Claude Artifact as-is, unlike the frozen `pme-mobile-sheet.html` prototype — it loads `engine.js`/`game.js`/`main.js` as separate `<script src>` files and `game.js` `fetch()`s JSON data files from disk at runtime, none of which an Artifact's sandbox can resolve. Getting the real engine onto an Artifact would need a bundling step first (inline the JS files, inline the JSON data, shim `fetch`) — not done as of 2026-07-23; local-server access is the current path instead.
- **`npm run serve`'s static handler only resolves an exact `/` request, not a bare directory path like `/mobile/`** (only `/` gets substituted to `/mobile/index.html`; a request for the directory itself 404s). Any service worker or other `caches.addAll`-style precache list must list explicit filenames only, never a bare `'./'` entry — `caches.addAll` fails atomically on the first 404, so the whole install silently never completes and `navigator.serviceWorker.ready` hangs forever with no visible error. Hit this building `mobile/sw.js` 2026-07-23.
- **After any change to AI investment aggressiveness or behavior (e.g. `mobile/game.js`'s AI personality profiles), re-run `npm test` plus a stress test that specifically hammers cheap/tiny states, not just the normal test suite.** A more aggressive AI can drive a state to exactly 100% ownership for the first time, which can surface latent redistribution-engine edge cases (a proportional-split branch with a zero denominator) that ordinary play never reaches — this is exactly how a real invariant bug in `engine.js`'s `loseAt()` was found 2026-07-23, undetected until then despite the existing test suite passing throughout.
- **Headless Node-based AI testing (`mobile/simulate.js`, or any ad-hoc script that calls `G.runAIFull()`) is an upper bound on AI strength, not a match for the real browser opponent.** `runAIFull()` has no pacing limit — it resolves a whole phase's worth of actions instantly. The real browser AI is throttled via `mobile/main.js`'s `scheduleAITick()`/`planAITickPacing()` to act at a human-comparable pace across the phase. A throttled-vs-unthrottled comparison found the throttled AI leaving up to 68% of its lifetime budget unspent in some seeds before this was fixed (2026-07-25) — any future AI-strength conclusion drawn from headless simulation alone should be treated as provisional until checked against, or explicitly caveated against, the real paced behavior.
- **Playwright testing notes for this project, confirmed 2026-07-24:** (1) use `page.clock.runFor()`, not `fastForward()`, when a test needs to simulate elapsed time against a `setInterval`-based app timer (e.g. the phase countdown) — `fastForward` only fires a repeating interval once regardless of how much virtual time is passed, `runFor` fires every due callback. (2) Chromium is a valid substitute for *screenshotting* the politician-select carousel and end-of-game overlay (it hits the same ~980px no-viewport-tag fallback as Safari, so the visual result matches) — the existing webkit-only rule below still applies to anything touching the shared gameplay chrome. **Correction, same day, later in the session: the claim that these overlays were "authored directly at real mobile scale" was wrong — see the 2.5x-scale convention bullet below; that mismatch is exactly what caused the text-too-small bug this correction is attached to.** (3) If a WebKit `page.screenshot()` hangs on "waiting for fonts to load," don't just raise the timeout — that has happened in this environment even when the page itself (`document.fonts.status`, console, DOM) is already fully loaded and error-free; verify page state directly first, then fall back to Chromium per (2) if applicable. (4) Any Playwright DOM measurement on this app (`getBoundingClientRect()`, `clientHeight`, `window.innerHeight`) is reported in that same inflated ~980px canvas coordinate space, not real device px, even when you pass an explicit `viewport` matching a real device — multiply by `(real device CSS width / 980)` before comparing against a real device's available height/width budget. (5) Jawaharlal Nehru's special-power description (266 chars, `data/politicians-data.json`) is by far the longest of all 20 politicians' (next-longest is 129) — use his card (carousel index 9) as the standing worst-case layout check for any future ballot-card sizing change; if his card fits without scrolling, the rest reliably do too. (6) `object-fit:cover` on a full-bleed background image can crop noticeably tighter on a real phone than a Playwright screenshot predicts, even using the `devices['iPhone 14']` preset — confirmed 2026-07-25 building the welcome screen's poster background, where a real device sliced a face at the screen edge that had full margin in every emulated screenshot. Don't trust an emulated screenshot alone to judge crop tightness on a `cover` image where cropping the edges would cut off meaningful content (faces, text) — verify on a real device, or default to `object-fit:contain` instead.

## Frontend technical rules

- Never rely on CSS Grid shrink-to-fit with `1fr` tracks when a declared pixel/icon size needs to actually hold — the grid container's width goes undefined and the browser silently overrides the item's declared size to fit an accidental viewport computation. Give the grid container an explicit, screen-relative width (e.g. `min(calc(100% - Npx), cap)`) instead. This already caused a real, hard-to-spot sizing bug in a mobile prototype's icon grid.
- Every standalone HTML file (prototype or real game) must declare `<meta charset="UTF-8">` as the very first tag. Claude's Artifact hosting sets the correct charset header automatically, but any other host (a local dev server, GitHub Pages, etc.) may not — without the explicit tag, every emoji, the ₹ symbol, and em dashes render as mojibake.
- When sizing mobile UI chrome (buttons, text, icons) in a prototype meant to represent real device proportions, calibrate against the actual iPhone 14 viewport (390×844, this project's default target) — not against how it looks inside the Claude Artifact viewer. The Artifact viewer wraps pages in its own ~150–200px title-bar chrome, which makes a `flex:1` map region look shorter than it will on a real device, and everything sized to "look right" against that preview reads as too small once viewed full-screen.
- A collapsible tray/panel (`max-height:0; overflow:hidden` to hide, animated open) still occupies its full declared *width* as a flex sibling even while collapsed to zero height — this silently inflates the gap between adjacent elements in the same flex row. Take it out of normal flow with `position:absolute` (anchored to a `position:relative` wrapper around just its own toggle button) instead of relying on collapsed height alone to make it width-neutral.
- For alternating-row hex/brick (honeycomb) layouts, give neighboring rows differing item counts (N, N−1) and center each row independently (`justify-content:center`) — no manual horizontal offset/margin needed. An N-item row and an (N−1)-item row, both centered on the same container width, differ by exactly half a hex+gap pitch, which is the correct honeycomb interlock offset for free.
- Safari-specific mobile bugs (viewport meta behavior, safe-area-insets, dynamic toolbar) must be verified with Playwright's `webkit` engine + an iPhone device profile (`devices['iPhone 14']`), not Chromium — Chromium ignores the page's own `<meta viewport>` tag even with an explicit viewport size set, so it cannot reproduce this whole class of bug.
- Playwright's `devices['iPhone 14']` preset sets `viewport: {width:390, height:664}`, not 844 — 844 is only the preset's `screen` field (the physical panel), modeling real Safari's chrome-reduced usable content area. Judge whether Booth Ink's ~755–765px fixed chrome will fit against 664px, not 844px, when reasoning from a Playwright screenshot — and treat a real device or Capacitor-wrapped build as the final check regardless, since headless webkit still isn't a perfect stand-in for Safari on this specific viewport-fallback behavior.
- Booth Ink (`pme-mobile-sheet.html`) intentionally has no `<meta name="viewport">` tag — its fixed-height chrome (header + news ticker + groups bar + info panel, ~755–765px) doesn't fit within a true 390×844 device-width viewport in a plain Safari tab, only within Safari's fallback ~980px virtual-canvas mode that a missing viewport tag triggers. Don't add a viewport meta tag here without first trimming chrome density, or confirming standalone/home-screen-installed mode is the actual deployment target.
- Booth Ink's map SVG renders 3 states (Uttarakhand `INUT`, Ladakh `INLA`, Himachal Pradesh `INHP`) as a duplicate-ID `<circle>` overlay layered on top of their real `<path>` boundary. Any map interaction code (paint, click, highlight) must query `path[id], circle[id]` together — targeting `path[id]` alone silently breaks these three states.
- Use `fill-opacity` (not `opacity`) to dim SVG map states — plain `opacity` fades the stroke/border along with the fill, which can make a dimmed state's outline disappear entirely.
- **Any element toggled via the `hidden` attribute needs an explicit `<selector>[hidden]{display:none}` rule if that same selector's base class already sets its own `display` value** — author CSS beats the browser's default `[hidden]{display:none}` UA-stylesheet rule at equal specificity, so `el.hidden = true` silently does nothing without it. Confirmed 4 times in this codebase now (`.overlay`, `.group-readout`, `.target-banner`, `.vs-bar`) — treat it as a checklist item whenever a new toggleable block gets its own `display` (flex/grid/etc.) in its base rule.
- **A decorative flex item with no intrinsic content (an empty-span color stripe, a bare spacer div) needs an explicit `width:100%` — it silently collapses to zero width whenever its flex-container parent's `align-items` isn't the default `stretch`.** The same `.tricolor` rule rendered correctly on the select-screen ballot card (parent has no `align-items` override) and was completely invisible (0×0 bounding rect) on the end-of-game card (parent sets `align-items:center` to center the seal/headline). Found 2026-07-24 — don't assume a rule ported from one flex context behaves the same in a sibling one with different alignment.
- **Any UI in `mobile/index.html` must be authored at ~2.5x the visually-intended font/padding/gap/icon size, not real-world size.** This app has no `<meta viewport>` tag (see the Local dev bullet below on why), so WebKit/Chromium both render it on a virtual ~980px-wide canvas and zoom the whole page out ~0.4x to fit the real device (`window.visualViewport.scale` measures 0.398–0.401). The in-game HUD (`.phase-chip`, `.iconbtn`, `.action-btn`, etc.) is already authored this way — e.g. a 35px phase-chip font renders at a normal ~14px real size. The politician-select/end-game ballot-card CSS was originally authored at literal real-world sizes instead (19px name, 13px body text), so it rendered at ~40% of intended size — reported as "text too small and unreadable," fixed 2026-07-24 by scaling every font-size/padding/margin/gap/icon-size in that CSS up ~2.5x. **Exception: leave border-width, box-shadow offsets, and `:active` press-transform values unscaled** — confirmed those are always authored small (1–3px) everywhere in this codebase regardless of whether the rest of a rule is scaled (ballot-card's `border:3px solid` and in-game `.iconbtn`'s identical `border:3px solid` render at the same real thickness on purpose).
