How the game actually works

PradhanMantri Elections Game is a 10-phase election simulation played on a map of India: invest cash, deploy rally tokens, commit to policy agendas, and pull a state's popularity away from your rival and the undecided middle until one side clears 272 of 543 Lok Sabha seats. This page explains the mechanics for players and the implementation for developers.

Authoritative for finalized design (ADR-0011) Verified against v2.7.5 Last full pass 2026-09-05

Play — the shape of a match

How a match works

Two players, no accounts, ten timed phases. Everything else in this document is a way of moving one number: your share of a state's popularity.

🕐 Structure

10 phases, ~45s each. Both players act simultaneously — there's no turn order within a phase.

💰 Funds

Start with 5,000 Cr, refresh +2,500 Cr per phase per player, independently.
Lifetime budget: 5,000 + 2,500×10 = 30,000 Cr

🗺️ Seats

Each state's Lok Sabha seats split proportionally to popularity share (largest-remainder apportionment, not winner-take-all).

🏆 Win condition

First to 272 / 543 national seats wins. Both under 272 after phase 10 → hung parliament.

Hung parliament is always a draw now, regardless of who's on the other side — ADR-0010, revised 2026-07-28, supersedes ADR-0006's original "draw vs. a human, loss vs. the AI" rule. That asymmetric version was dropped once mobile/balance-sim.js measurements showed hung parliament actually landing 48–98% of games per politician on the now-harder-to-win roster — defaulting that many undecided matches to an automatic AI win would have made a disguised loss the modal outcome, not a rare edge case. This build is always human-vs-AI, since live matchmaking isn't built (see Architecture) — though a full implementation-ready plan for it now exists.

Where the 30,000 Cr figure comes from

data/game-config.json → mobileEconomy sets startingFundsCr: 5000 and fundsRefreshPerPhaseCr: 2500 — deliberately bumped on 2026-07-24, double the original 2,500 / 1,000, after playtesting found the old budget too tight to realistically reach a majority. The design doc's Core loop prose and its Plausibility-check table hadn't been updated to match until this pass — now they are, and the table's win-margin figures widened substantially as a result.

Play — the one rule everything routes through

The map & the 100% rule

Every state always splits exactly three ways: you, your opponent, and Others — the undecided middle. Nothing is ever created; every action just reassigns a slice of that same 100%.

flowchart TD
  L["A lever fires:
cash tap · rally token · agenda tap · special power"] --> G["1. You gain the boost
— capped so you can never pass 100%"]
  G --> S["2. Opponent and Others each give up
their share of it, in proportion to what they currently hold"]
  S --> O["State popularity → seat share (proportional) → national win condition"]

Why basis points, not percent

Under the hood a state's popularity isn't "28.12%" — it's 2812 out of 10,000 basis points (bps). Splitting a gain between two recipients rounds one side to a whole number and gets the other by subtraction, never rounds both independently — that's the only way to guarantee the three shares always sum to exactly 10,000. Screens still just show "28%," rounded once, right at display time.

Worked example — a single tap

A state sits at P1 20% · P2 30% · Others 50%. P1 taps once for a flat +5%. P1 has headroom (20+5=25, nowhere near 100), so the full 5% goes through. That 5% comes out of P2 and Others in their existing 30:50 ratio.

P1P2Others
Before20.00%30.00%50.00%
After P1's tap25.00%28.12%46.88%

Verified against mobile/engine.js's self-check (gainAt, run via node mobile/engine.js): identical numbers, bit-for-bit. ✓

Worked example — two big plays collide on the same state

Turns are simultaneous, so both players can target the same state the same phase. Pulls on each other's share never collide — only pulls on Others can overdraw. When they would, both requests shrink proportionally to fit, like splitting a bill that's short on cash.

P1P2Others
Before — a contested small state10%10%80%
After — both fire a huge play, same phase50%50%0%

Only two levers are big/simultaneous-capable: a Nationwide Rally and a Special Powerup. Implemented as resolveSimultaneousGain() in engine.js, invoked through applyBigAction() in game.js.

Seats: largest-remainder apportionment, not plain rounding

Rounding each side's seat share independently can hand out more seats than a state has. A 3-seat state at 50% / 25% / 25% gives quotas 1.5 / 0.75 / 0.75 — round each separately and you get 2+1+1 = 4 seats from a 3-seat state. Instead: give everyone floor(quota) first, then hand the state's few leftover seats to whoever has the largest fractional remainder (ties broken by higher bps, then fixed order P1 > P2 > Others).

P1 (50%)1.5010.501
P2 (25%)0.7500.751 ← largest remainder
Others (25%)0.7500.751 ← tied, but ranks above P1's 0.50

Play — before the first phase even starts

Starting position

Not a blank map and not a fixed table — generated fresh per match, per politician pair, in a strict three-step order.

1️⃣ Baseline

Every state gets an independent random 5%–29% for each player. Others holds the rest, everywhere.

2️⃣ Home state

Your politician's homeState gets +25% on top of your baseline (capped at 100%). Same home state on both sides → the bonus is nullified for both, not split.

3️⃣ Random draw

Both home states are pulled from the pool. Players alternate drawing (coin-flip who goes first); each drawn state gets a fresh 35%–65% for the drawer, until their seat-budget counter exceeds 145 (never past 181) — and that counter now starts pre-loaded with 25% of the player's own home-state seats, not zero (see the note below).

A politician can have more than one home state

The additive secondaryHomeStates array (added 2026-07-25 for Kejriwal, ["Punjab"] alongside his primary Delhi) exists because Delhi's 7 Lok Sabha seats made the standard +25% bonus far weaker in absolute terms than for politicians whose home is a bigger state. Every consumer of homeState — the starting-position generator, the home/opponentHome special-power scopes, the display line — has to read through a shared helper rather than the raw field directly, or a multi-home politician silently loses the bonus in whichever spot still reads homeState alone. The "shared home state nullifies for both players" rule now applies per overlapping state, not per player.

Why Uttar Pradesh's over-representation is a feature

9 of the 21 politicians call Uttar Pradesh home. That sounds like a balance problem, but it means the home-state-tie nullification rule triggers often — which is exactly what stops one player starting with a lopsided lead just by picking a UP-born politician and claiming the country's single biggest state (80 seats) uncontested.

2026-08-26 fix: home-state seats now count against the same draw budget

The random-draw thresholds (124/154 at the time) were calibrated for a ~150-seat mean with ~175 at 2-sigma, but that calibration assumed the draw started from a budget of zero — home states were fully excluded from the draw pool and got their +25% for free, on top of that budget, not against it. Invisible for a typical single small-to-medium home state, but it broke down for a large one (Uttar Pradesh alone pushed the mean to ~156.6) and especially for a multi-home politician (Hema Malini's Uttar Pradesh + Tamil Nadu pushed it to ~166.2, with real games landing above 200). Fixed by seeding the draw-budget counter with 25% of each player's own home-state seats (2500/10000 BPS — the home bonus's own magnitude, since apportionment scales roughly linearly with a flat vote-share addition) instead of zero.

That fix alone pulled the overall mean down too far (~147 → ~143 across a 1000-game simulation using real random matchmaking), since it made every politician's home state compete for the same budget, not just the previously-broken large/multi-home ones. Re-tuned the thresholds themselves the same day (124/154 → 145/181, now named DRAW_BUDGET_STOP_AT/DRAW_BUDGET_MAX) to restore the target: confirmed via the same 1000-game methodology at mean=150.3, sd=12.4, max=192 (Hema Malini, still the roster's highest/most variable starter by design — a real, deliberate edge over a single-home baseline since this roster's celebrities are meant to feel OP along varied axes, not just via their special power — but nowhere near the 213-seat outlier that started this).

Implemented as generateStartingPosition() in mobile/engine.js. The 2026-07-23 playtest bug where this occasionally produced a 200-seat starting position instead of the intended ~100–130 range was traced and fixed before this document was written. The 2026-08-26 home-state-budget fix above is a distinct, later bug in the same function.

Play — the three levers you spend resources on

Money, rallies & agendas

Three ways to spend, each with a different shape of cost curve. All three ultimately just call the same redistribution rule above.

Direct cash investment

Tap #BoostNote
1+5.00%opening tap, best rate
10+3.58%linear glide
20+2.00%glide path ends
30+1.00%geometric decay past the glide path — halves every 10 taps
40+0.50%
50+0.25%
91++0.01%hard floor, flat from here on (max(1, …))

Cost per tap = state.seats × 10 Cr, always flat — only the boost decays. For the first 20 taps the decay is linear (500→200bps); past tap 20 it used to lock at a permanent 200bps floor forever, which meant a cheap 1-seat UT could be re-contested indefinitely at a fixed, still-meaningful cost. Fixed 2026-08-24 (v1.1.2): past tap 20 the boost keeps decaying geometrically instead of flattening, so repeated taps on the same state keep getting weaker. Slackened 2026-09-02 (v2.6.2), on a playtest report that the curve stalled out too abruptly: the decay rate went 0.85 → 0.933, i.e. the boost now halves every 10 taps past the glide path (tap 30 = +1.00%, tap 40 = +0.50%, tap 50 = +0.25%) where 0.85 gave +0.39% / +0.08% / +0.02%. There is a hard floor — max(1, …) pins the boost at 1 bps (+0.01%) forever — but the slower decay pushes that from tap 51 out to tap 91. Since cost per tap never decays, a 1-seat state's cost per +1% tops out at 1,000 Cr at the floor and a 30-seat state's at 30,000 Cr.

costPerTap(state) = state.seats × 10                                // Cr
boost_bps(tap) = tap ≤ 20 : round(500 − (tap−1) × 300/19)            // 500 → 200 bps, linear
                 tap  > 20 : max(1, round(200 × 0.933^(tap−20)))     // halves every 10 taps; pins at 1 bps from tap 91

Why this mattered: a cheap state could veto an expensive group forever

Regional dominance requires every member of a group at 50%+ (see below) — including groups that mix a 1-seat UT alongside 20-40-seat states. Under the old permanent floor, re-suppressing that one cheap UT cost the same 10 Cr per 2% forever, so it could deny access to a group worth hundreds of Cr in payout at near-zero ongoing cost. AI-vs-AI simulation (1,260-game full politician matrix, same seeds before/after): groups containing a small UT went from winning ~36% less often than UT-free groups (4.1% vs 6.4%) to statistically even (5.6% vs 5.7%); combined spend on the 7 smallest UTs fell ~71% per game; average final seats rose for both players (+8.3 / +7.3) as fewer seats got stuck contested with neither side ever converting them. This only stops sustained spam — a slow, occasional strategic snipe of the same state stays exactly as viable as before (each side's own tap-decay clock only advances on their own taps, so a low-frequency defender doesn't grind through it the way a constant attacker does).

Rally tokens

📢 Income

+2 tokens/phase/player, up to +8 more from completed agendas (max pool: 28 earned, but only 20 ever spendable at 2/phase × 10 phases).

🎯 Caps

Max 2 played per phase. Max 2 plays total per state — a shared lifetime pool across both players, not 2-each.

💥 Boost

+5% flat per play, no decay — same value as a completely fresh cash tap, minus the Cr cost.

Crafting: tokens become bigger plays

Spend 6 tokens (no phase gate — specialPowerupMinPhase was dropped 3 → 0 once 6 tokens turned out to be reachable in round 1 from agenda completions alone, which made the gate arbitrary on already-earned resources) → craft a Special Powerup, the one-time activation of your politician's unique power. Spend 12 tokens (earliest phase 6) → craft a Nationwide Rally: +5% applied to every state at once, one use per game. 12 tokens spent individually could reach at most ~10 states before the per-state cap bites; the sweep is what makes Nationwide Rally worth 60% of a lifetime token budget.

The per-state cap is a shared pool — deliberately

Because the 2-play cap is shared, either player can burn both slots on a state early specifically to lock the other side out of it entirely — a denial play, not just a boosting one. Symmetric and confirmed intentional, same category as "sabotage is cheaper than conquest" under Regional Dominance below.

Agenda commitment

Each politician carries 4 agendas drawn from a shared 32-policy pool (data/policy-tags.json — 25 as of the last count, plus 7 new tags added 2026-08-21 in a thematic-distinctiveness pass: Coastal Economy, Food Security, Heritage and Tourism, Environmental Conservation, Sports and Entertainment, Nationalization, Foreign Policy & Diplomacy. The same pass retired Judicial Activism — it had no real signature fit for anyone but Ambedkar, and even that was a stretch — repurposing its pool slot into Administrative Reform, now held by Ambedkar and Sardar Patel). Each agenda costs 500 Cr per tap, flat, 4 taps to max (2,000 Cr/agenda, 8,000 Cr to max all 4 — 27% of the 30,000 Cr lifetime budget). Agendas aren't a race — each player only ever funds their own 4; there's no way to contest a policy away from an opponent.

Net-first, apply-once — the rule every agenda tap follows

A state can carry several of a policy's region tags at once, some supporting, some opposing, each at its own signed strength. The engine sums every matching tag into one net value for that state before touching the redistribution engine — never applies each tag as a separate transaction. National Defense supports the border regions and used to also (accidentally) oppose Hindi Heartland; six of the largest states carried both tags and canceled to exactly zero, quietly zeroing out states that should have been the policy's strongest supporters. Fixed 2026-07-22 by dropping the stray oppose tag.

Completion isn't held back to the end either: each of the 4 taps immediately fires ¼ of the state's net effect through the redistribution engine (agendaTapDelta() in engine.js, using the same round-cumulative-then-diff trick that keeps rounding exact across more than two shares). Completing an agenda also grants +2 rally tokens, up to +8 across all four.

Every tagEffects magnitude is one of ±4/±8/±12 — added 2026-08-26; further tuned 2026-09-02

A handful of ±6/±10 outliers (Administrative Reform, Coastal Economy, Food Security, Heritage and Tourism, Environmental Conservation, Sports and Entertainment, Nationalization — 12 individual values across 7 policies) were normalized onto this convention in v1.3.0. It exists so the new agenda emoji reaction feature can read a policy's real per-region pull directly (agendaGroupEffects() in mobile/game.js — a policy's tagEffects region keys are exactly the 15 regional-dominance groups' own keys, one-to-one) rather than simulating a tap's actual redistribution outcome. Tapping an agenda you (the human player) control now briefly pops an emoji over each affected group's chip: 🙂/🙁 for ±4, 😄/😟 for ±8, 😍/😡 for ±12 — AI agenda taps don't trigger it. Some of the normalized values had been deliberately off-convention specifically to dodge a same-state cancellation against another of that policy's own tags; 5 such collisions were knowingly reintroduced as an accepted tradeoff (Administrative Reform in Madhya Pradesh, Environmental Conservation in Jharkhand, Nationalization in Andhra Pradesh/Tamil Nadu/West Bengal) — see CLAUDE.md for the exact tag pairings. The seat-equivalent ranking table below predates the 2026-08-26 normalization and is stale for these 7 policies. Update 2026-09-02: four policies adjacent to the Manufacturing group were stepped down one rung each (Rural Development -8→-4, Land Reforms +8→+4, Agricultural Reforms -8→-4, Economic Liberalization +12→+8) to prevent new cancellations when Manufacturing added agricultural states (Punjab, Rajasthan, Andhra Pradesh). The ranking table is now also stale for these four; see CHANGELOG 2.6.0 for the rationale and findings.md [F3] for the full cancellation audit.

Play — one signature move per politician

Special powers

Every politician has exactly one unique power, activated once per game by crafting a 6-token Special Powerup. The rule that governs every one of them: resolve instantly only, and cost a genuine resource — never a timing gate ("only in the final phase") or an eligibility condition ("only while behind") — because either of those costs nothing whenever the power is actually usable.

Explicit exception: six powers ARE timing-gated, on purpose

Sardar Patel's Iron Unification (requiresMinPhase: 5), Narendra Modi's Demonetization (3), Indira Gandhi's National Emergency (5), B.R. Ambedkar's Constitutional Reform (3), P.V. Narasimha Rao's Minority Government Survival (6), and Amitabh Bachchan's Celebrity Endorsement (6) all block activation before a specific phase (mobile/game.js's activatePower and the AI's canPay check both read the field). Each is a deliberate flavor call mimicking the real-world timing of the event it represents (Patel's unification took years; Modi's 2016 demonetization landed mid-term; the Emergency came deep into Indira's tenure; the Constitution took ~3 years to draft; a minority government only means something once a majority looks out of reach). The first five were decided 2026-07-26; Bachchan's was added later, in the celebrity-power rebalance that also cut his nationwide swing 12% → 6% and raised his cost ₹1,000cr → ₹2,000cr — the gate is part of that nerf, not a flavour call, and is the one exception on this list without a real-world timing rationale. None of them is an oversight of the no-timing-gate rule above, and the rule stands: no further power gets a gate without the same case-by-case justification.

All 21 now carry concrete numbers

Six powers were reworked 2026-07-22 after failing the matched-cost-and-benefit rule outright (see table below). The rest, including Vajpayee's reviewed-and-kept Pokhran Test, all carry real numeric costs and benefits in data/politicians-data.json today — verified directly, entry by entry. This was a first-pass assignment, not a balance/playtesting pass when originally written — that gap has since been closed by mobile/balance-sim.js (see The AI opponent), which found three politicians (Rahul Gandhi, Mamata Banerjee, Manmohan Singh) genuinely bottom-tier and four "OP" celebrity/film-persona powers over-tuned; both findings drove real rebalances, not just a numbers pass.

Confiscate vs. transfer: "seize" and "steal" are deliberately different primitives

A power that takes the opponent's resources must choose explicitly between seize (seizeFundsPct/seizeTokens — confiscated, destroyed, never reach the activator) and steal (stealFundsPct/stealTokens — transferred to the activator). Kejriwal's Anti-Corruption Raid, Indira Gandhi's National Emergency, and Sivaji Rao's original One-Day Ordinance were all built on the transfer primitives by default; corrected 2026-07-26 once "raid"/"seizure"/"confiscation" framing was clarified to mean the opponent's resources vanish, not that they move to you. It changes each power's real value, not just its wording — Kejriwal's Anti-Corruption Raid now reads "seizes 50% of the opponent's cash (destroyed, not transferred)," and Indira's National Emergency seizes 100% of cash plus all rally tokens.

Reference point

Vajpayee's Pokhran Test (+8% nationwide, zero extra cost beyond the 6-token craft) is a deliberate outlier — exactly 1.6× Nationwide Rally's boost (5%) for half the token cost — kept on purpose as the roster's one standout "signature" play, and used to sanity-check every other power's magnitude during the rework pass. Tuned down from +10% on 2026-08-28 per balance analysis showing seat gains exceeding 50-seat threshold.

The 4 celebrity/film-persona powers were rebalanced 2026-07-28 — agenda kits left untouched

Decided 2026-07-25: Tendulkar, Hema Malini, Rajinikanth, and Bachchan are meant to be stronger and quirkier than the political roster, not balance-equal to it — each carries a distinctive mechanic shape (a 30%-floor effect, a stacked nationwide+home bonus, an asymmetric dual-region bonus, an "Others"-only source) and is explicitly allowed to out-scale a political-roster power in the same region. But a 2026-07-28 balance pass found these 4, plus film-persona pick Sivaji Rao, had both a top-tier agenda kit (national avg 13–16, roster-highest) and a strong/free power stacked on top — an unintentional tuning error, not the design intent. Rebalanced on the power only — cost, timing, or magnitude — never the agenda kit, which stays a deliberate thematic match:

Two methodology lessons from tuning this: a single-politician change must be re-tested isolated (that politician's data changed, every other politician held at the exact same committed state) before trusting a before/after win-rate comparison — a batch where other politicians also changed is confounded by "strength of schedule." And a single lever (cost, timing, or magnitude alone) hits diminishing returns fast — Bachchan's cost/timing changes alone moved his win rate by exactly 0% until paired with the magnitude cut.

Two more power reworks, 2026-08-21 — Modi's bottom-tier win rate, Rajinikanth's outlier win rate

A fresh balance-sim.js run after the 7-tag thematic pass showed Modi bottom-tier (43.5% win rate, tied lowest in the roster — thematically wrong for India's most-elected real-world PM) and Rajinikanth a sharp outlier (72.5%, ~13pt above the next-highest). Both fixed on the power only, same discipline as the 2026-07-28 pass above — Modi's agenda kit (Infrastructure/Hindutva/Economic Liberalization/National Defense) was already judged thematically solid, so it stayed untouched.

Rajinikanth — Thalaivar Announcement: the existing −8% Hindi Heartland penalty wasn't enough on its own. Deepened to −14%, magnitude trimmed (+25%→+22% South India, +18%→+15% Maharashtra), fund cost tried at 3,000 Cr then reverted to 2,000 Cr once the −14%/magnitude trim alone proved sufficient. Result: 72.5% → 59%, no longer an outlier.

Modi — Demonetization: two independent single-lever attempts (cheaper: −5%→−2% popularity cost; longer: 1 phase→2 phases, via fundsFrozenUntilPhase in mobile/game.js switching from an equality check to a range check) each moved his win rate by ~0% — a real confirmation, not noise, that a pure-denial power's problem is its shape, not its cost or duration: it gives Modi nothing directly, so its payoff depends entirely on the AI capitalizing on the opponent's frozen phase, which it doesn't reliably do. Fixed by adding a direct, unconditional benefit — +4% popularity nationwide alongside the freeze, no separate cost (an earlier +6%/−2% split was simplified to a clean +4% once flagged as needless — same net effect, one line instead of two). Result: 43.5% → 54%.

Methodology note for future rebalancing: this session is direct evidence that balance-sim.js's AI-vs-AI win rates undervalue conditional/exploit-dependent powers relative to unconditional/guaranteed ones — the AI (a greedy heuristic, not adversarially tuned; see The AI opponent) doesn't reliably play around an opponent's disadvantage the way a skilled human would. Before nerfing (or writing off as weak) any power whose value depends on smart timing or targeting rather than an instant guaranteed effect — Yogi's targeted Bulldozer Action, Nehru's contingent Non-Alignment — read its measured win rate as a likely floor, not its true ceiling in human play. Full methodology lives in design/testing-and-balance-notes.md.

Play — an incidental kicker, not a target to chase

Regional dominance

15 groups of states (5 large / 5 mid / 5 small by seat count) pay a cash bonus the instant every single member state is simultaneously at 50%+ for one player — not a seat-weighted average.

dominanceActive(group, player) = every state in group: player's share ≥ 50%
payout(group) = 5 Cr × (sum of seats across every state in the group)

Worked example — the cheapest group in the game is still a bad standalone target

Agricultural Region (273 seats) pays 5 × 273 = 1,365 Cr. Pushing every member state to 50% from a cold start costs roughly 12,480 Cr at the real decay curve — about 11% ROI, the best case of all 15 groups. Every group costs more to fully dominate from scratch than a large fraction of a lifetime budget. It only pays off as a bonus on top of states you're already winning for the main seat race.

Sabotage beats conquest

One state slipping under 50% zeroes the whole group's qualified status immediately — no more payouts until every member re-crosses the line. That makes "knock one state back down" a cheaper counter-play than "out-invest the leader everywhere." Deliberate, not a bug. What's no longer free (fixed 2026-08-24, v1.1.2): permanently re-knocking down the same cheap state, forever, at flat unchanging cost — see the investment decay-curve note above.

Education & Manufacturing group rebalance — added 2026-09-02, v2.6.0

The Education and Manufacturing regional-dominance groups shared 5 of ~7 states (Jaccard overlap 0.50) before this session, making them near-synonyms thematically and structurally. Manufacturing was regrouped to MoSPI's top-10-by-registered-factories list minus Uttar Pradesh (which the user explicitly rejected as too large): added Punjab, Rajasthan, and Andhra Pradesh; removed West Bengal (not in top 10). Education gained Assam (previously in neither group). Result: symmetric-for-the-first-time design with Education-unique 5 states/84 seats, Manufacturing-unique 5 states/99 seats, Jaccard reduced to 0.29. This also makes both groups harder to capture, not easier — each new state is another AND-gate veto point, and 1,260-game measurement confirmed Manufacturing's capture rate fell 78.7%→69.4%, Education 80.5%→76.7% (see findings.md [F6] for the counter-intuitive direction). Four policies that opposed both Manufacturing and AgriculturalRegion at matched magnitude (Rural Development, Land Reforms, Agricultural Reforms, Economic Liberalization) were stepped down one rung in magnitude to prevent new same-state cancellations introduced by the new agricultural states; no politician's national kit average moved more than 1.3 points (negligible). See CHANGELOG 2.6.0 and findings.md [F3] for the full rationale and cancellation audit.

Payout is instant and event-based (changed 2026-07-24) — it fires the moment the last member state crosses 50%, checked after every popularity-moving action, not deferred to the next phase boundary. Losing and re-earning dominance pays again in full each time. Implemented as applyRegionalDominancePayouts(), called (via the shared applyPayouts() wrapper — see below) from every action that can move a state's popularity.

Group holding bonus — added 2026-08-25, v1.2.0; tuned v1.2.1, v1.2.7, v1.3.1

A smaller, flat, recurring sibling to the instant bonus above — thematically "sustained popularity keeps drawing fundraising." Pays at the start of every phase a group is still held (checked via the same dominanceActive() the instant bonus uses, just triggered at a different point — applyGroupHoldingBonus() in mobile/game.js, called once per phase boundary from startPhase(), never from the mid-action applyPayouts() wrapper). Currently 0.5 Cr/seat (holdingBonusCrPerSeat in game-config.json's mobileEconomy.regionalDominance) — dialed down from 5 (v1.2.0) to 2 (v1.2.1) to 1 (v1.2.7) to 0.5 (v1.3.1) as too strong relative to the one-time instant dominance payout, which stays at 5 Cr/seat. Deliberately flat: doesn't grow the longer a group is held, so it can't compound into a late-game blowout on top of the instant bonus. `dominanceHoldingPayoutCr()` rounds its result as of v1.3.1, since a fractional per-seat rate combined with several groups' odd seat counts would otherwise show a fractional Cr amount in the log/toast.

Win rate in symmetric AI-vs-AI simulation stays flat as magnitude increases (expected — both players get it equally), which is why that harness alone didn't catch the real risk: it's paid per group, not deduplicated across a state that belongs to several groups at once (15 overlapping groups exist, several 200+ seats each) — so an asymmetric capture (one side sweeping most groups, the other none) can mean 1,000+ "group-seats" worth of payout every single phase, entirely one-sided. Found 2026-08-26 from a user report of a 341-143 blowout after capturing 7 of 15 groups against an AI that captured 0 — the recurring bonus turned an early group-capture lead into a compounding late-game snowball the symmetric AI-vs-AI harness structurally can't see, since it requires one side to actually dominate group capture the way a human beating a passive AI does. The 1 Cr/seat cut (v1.2.7) plus the AI rally-cap fix from the same session weren't enough on their own — a further user report of a still-lopsided blowout led to halving it again to 0.5 (v1.3.1). If blowouts persist at this level, the next lever to check is whether `group-bonus-rusher` is actually getting picked often enough as the AI's profile, not the bonus magnitude itself — see the AI-profile note above.

Group-chip completion ring — added 2026-09-02, v2.6.0

Each regional-dominance group displays a live two-layer conic-gradient ring border showing seat-weighted progress toward completion. P1 fills clockwise from top, P2 fills anticlockwise; an unclaimed remainder is transparent. Implemented via dominanceProgress(group, states, pop, player, thresholdBps) in mobile/engine.js (returns 0–1 based on seat-weighted group completion), read at render time and applied as CSS `--ring-p1` / `--ring-p2` variables on each chip. Deliberately seat-weighted, not state-count-weighted, after playtesting feedback: the ring shows how much of a group's VALUE you hold, not how close to the all-or-nothing gate — a 99%-held ring can be one 1-seat holdout from paying nothing, an accepted trade-off for showing real progress rather than the binary state-count metric. Captured on the group's `renderGroupCaptureBadges()` via edge-detect (false→true transition) for the dedicated `bell_chime` sound — replaces the earlier log-string-match pattern that fired `fanfare` at the wrong time (see findings.md [F7]).

Clean sweep bonus — one state at a literal 100%

Added 2026-08-17. A smaller, single-state sibling to regional dominance: the instant a player's share of one state hits an exact 100% (opponent and Others both at 0), they get a one-time 5 Cr/seat payout — same rate as regional dominance's per-seat rate, same instant/held/re-payable shape (applyCleanSweepPayouts(), tracked in game.cleanSweepHeld). Both payout checks now run together from one applyPayouts() wrapper at every call site that used to call applyRegionalDominancePayouts() directly. Scaling by the state's own seat count (not a flat amount) is deliberate — a flat bonus would re-open the old "cheap tiny UTs are disproportionately attractive" AI-targeting bug (see the greedy-scoring discipline bullets in CLAUDE.md). Also drives a live visual: any state currently at 100% for a player gets a colored glow on the map (.swept-p1/.swept-p2 in mobile/index-redesign-a.html, toggled in paintMap() — a live read of game.pop, not the payout-gating held flag, matching how the group-dominance capture badges already work).

Play — what carries between matches

Progression & meta

Everything outside a single match lives in the browser's localStorage, on that device only. There are no accounts and no server. It is deliberately client-side and devtools-bypassable — a single-player nudge, not anti-cheat; closing that hole needs a real backend, which is out of scope until multiplayer is.

Unlocking the roster

🔓 Three to start

Modi, Manmohan Singh and Vajpayee are unlocked from the first launch. The other 18 are earned by beating them as the AI opponent.

🎲 Weighted draw

70% of the time the AI opponent is drawn from politicians you have not unlocked yet, so the roster does not stall out on luck once only a few names are left.

💎 Ink charges

Each politician has 3 charges (the diamonds on their card). Playing them spends one; at zero they are out of ink for a 6-hour cooldown, then refill to 3.

🛟 Fail-open

If storage is unavailable or corrupt (private browsing, quota), the loader returns null and everyone is treated as unlocked — a storage failure must never softlock the roster.

iOS caps script-writable storage at 7 days unless the app is installed

Safari's ITP purges localStorage and the Cache API after ~7 days of inactivity for a site that is not on the home screen. There is no code fix — the only mitigation is prompting the player toward Add to Home Screen, which is also what the phone-only #installGateOverlay does. That gate fires for a coarse pointer under 700px wide that is not already in standalone display mode; desktop and tablets skip it, since after the v2.0.0 viewport migration the layout reflows and plays fine in a tab at that width.

Final score

A single composite number computed at game end by computeScore() in mobile/game.js, from weights in game-config.json's mobileEconomy.scoring. It is a pure function of final game state, which is the point: the same number is reproducible server-side from a replayed action log, so it can back a leaderboard later without trusting the client's arithmetic.

ComponentWeight
Final seats× 100
Seat margin over the opponent (never negative)× 50
Outcome+50,000 win · +15,000 draw · 0 loss
Regional-dominance groups held at the end× 4,000
Agendas completed (all 4 taps)× 1,500
Clean sweeps (a state at exactly 10,000 bps)× 2,500

Everything is scaled ×100 so the number reads big. These are first-pass weights, meant to be tuned against beta feedback rather than simulation. The clean sweep also pays cash in its own right — cleanSweep.payoutCrPerSeat, currently 5 Cr/seat — once per sweep, not every phase it is held, and again if the state is lost and re-swept. simulate.js asserts exactly that.

Replay

Every game records an input log (game.actionLog) alongside its RNG seed, and replay re-runs those inputs through the real engine rather than playing back stored outcomes (ADR-0014). That is what makes the score reproducible — and also means an engine change version-locks old replays, which is an accepted tradeoff, not a bug. npm test asserts every simulated game replays from seed + log to identical final seats. The last game is kept under pme:lastReplay; a quota or private-mode failure to save it still leaves the in-memory replay working for that session. Input is locked while a replay (or a pause) is running.

Tutorial

Two stages, both optional and both driven by step tables in main.js: 5 steps on the select screen (TUTORIAL_STEPS — browsing the carousel, agendas, special powers, then a gated first Play, locked to Modi), and 34 steps in-game (TUTORIAL_STAGE_STEPS), which gate actions sequentially against live game state. The phase timer and the AI auto-pause during a step, so nothing is rushed. The tutorial game runs on a fixed seed with dynamic funds grants so the scripted path always succeeds regardless of the draw; neither applies to a normal game, and the tutorial's completion is not a rated match, so it cannot move the difficulty ladder.

Two playtest switches that must be false in any deployable commit

UNLOCK_ALL unlocks the whole roster and waives the install gate. PLAYTEST_BUILD gates everything else that can bypass progression — the long-press playtest toggle and forcing the human's politician via ?vs=/?p1=. scripts/deploy-mobile.js refuses to ship PLAYTEST_BUILD: true, so that one is enforced rather than remembered. The older ?p2= and ?ai= hooks stay ungated deliberately: they only choose your opponent or the AI's difficulty and can never reach a politician you have not earned. The distinction is the point — the unlock progression is meant to be bypassable with devtools, but not by accident, by a curious player prodding at the footer or pasting a shared link.

Build — how Player 2 thinks

The AI opponent

One greedy heuristic in mobile/ai.js, not an adversarially-tuned agent. It plays through aiStep() — one action per call — so the browser can pace it visually (~20 actions/min) while runAIFull() fast-forwards the same logic instantly for tests. Difficulty is not a second bot: it is a set of feature flags read off pl.aiProfile by that one heuristic.

Priority order, every tick

1. Rally

One attempt per tick at a value-weighted random pick from the largest states — never a strict argmax, since the human draws from the same shared 2-plays-per-state pool. A rejected placement banks the token instead of retrying.

2. Craft

Special Powerup the moment 6 tokens are banked — unconditional, every rung. Nationwide Rally only if the profile crafts tokens.

3. Power

Activate the crafted power the moment it's affordable and its target requirements are met.

4. Nationwide Rally

Fire it the moment it's crafted.

5. Agenda

Tap the best-ranked policy, up to 4 taps/policy/phase. seatRankedAgendas ranks by real seat delta and skips any tap worth less than the same cash invested; without it, by raw totalNetEffect().

6. Invest

Otherwise, invest in one state-group at a time (round-robin, skipping groups already dominated) scored by effective headroom, not raw boost.

The difficulty ladder

Eight rungs (ADR-0016). Each rung is the previous rung plus exactly one capability flag, every other knob held constant, so the gap between rung N and rung N−1 is that one capability's worth in seats. Level 1 reproduces the old shipped policy-rusher bot exactly, so the bottom of the ladder is the difficulty the game actually shipped with rather than a newly-invented weak bot. The three other old personality profiles (aggressive-investor, rally-spammer, group-bonus-rusher) were flavour rather than difficulty and are gone — git history has them.

What each flag turns on

seatRankedAgendas — rank agenda taps by real seat delta, and skip any tap worth less than the same cash spent on investment. tokenDiscipline — bank rally tokens toward the Nationwide Rally unless a state rally beats it per token (only the two biggest states do). smartGroupTarget — chase the group with the best payout per crore still needed, re-picked live, instead of one random group fixed at game start. spreadInvest — invest for maximum delivered bps, dodging the per-state boost decay. groupObsession: N / groupCap: N — how many regional-dominance groups it will fixate on, or stop chasing new ones after.

Never read one flag's ablation delta as that flag's standalone value

Each rung's number above is conditional on every flag below it in the chain. Pulling one flag out of level 8 and measuring the drop tells you what that flag is worth given the rest, not what it is worth on its own — seatRankedAgendas measuring weaker than nothing at all when isolated is the proof. For AI-profile strength questions use mobile/ladder-sim.js (seat-margin round robin, mirrored pairs, monotonicity check), never balance-sim.js, which never varies AI profile and so cannot attribute a result to one. Re-run ladder-sim.js after any change to shared aiStep code.

Adaptive difficulty: one number the player can also drag

The level lives in localStorage under pme_ai_level, starts at 1, and moves on a 3-in-a-row streak — three wins promotes, three losses demotes, a draw does neither (updateLadderAfterMatch() in main.js). Only a rated match counts: game.ratedMatch is a one-shot flag set at game creation, so the tutorial sign-off path and replays cannot drift the ladder. The settings slider shows and sets the same number — there is no separate auto/manual mode, and no random difficulty (a random difficulty is a worse experience than a random personality was).

A human-facing restriction is not an AI restriction

The AI acts directly on game state and bypasses main.js's DOM layer entirely, so any rule enforced only by a disabled button or a batch-only control does not apply to it by default. Whenever a UI restriction is added, check the engine-level path for the same restriction — SMALL_UT_BATCH_IDS is the fix pattern. The same class of bug once capped the AI to one rally per phase via an aiRalliedThisPhase flag layered on top of the real maxTokenSpendPerPhase check, silently halving its rally usage against a human in every game; the flag is gone and the AI now rallies to the real shared cap.

Two rounds of scoring fixes in scoreInvestState()

Early versions scored an investment target by raw boost/cost, which kept favoring the cheapest state in a group regardless of how close it already was to 100% — the AI would dump funds into an already-maxed state forever instead of spreading across the group, so it could never actually clear a regional-dominance bar. Fixed 2026-07-23 by scoring on effective remaining headroom, min(boost, 10000 − currentShare) / cost. A second, distinct failure mode surfaced 2026-07-25: the score was still raw %-per-Cr, unnormalized by seats — cost scales with a state's seat count but the % boost per tap doesn't, so a 1-seat UT scored 20–50 against Uttar Pradesh's 0.25–0.6 even on UP's very first, most-boosted tap. The AI (and a human chasing the same "biggest % shown" intuition) hammered tiny states instead of spreading nationwide the way the design doc's cost-per-seat invariance claim assumes. Fixed as part of the broader AI investment-targeting rework the same day.

Even, human-comparable pacing — no instant catch-up burst

An early fix for the AI leaving funds unspent by phase end used an instant full-phase catch-up (runAIFull()) right before each phase closed. Rejected 2026-07-25 as unfair machine-speed cheating: AI strength should come from decision quality, never from acting faster than a human physically can. mobile/main.js's planAITickPacing() throttles the browser AI to a human-comparable pace (~20 actions/min) across the whole phase instead — this is also why headless simulation (runAIFull(), no pacing limit) is an upper bound on AI strength, not a match for the real opponent; a throttled-vs-unthrottled comparison once found the throttled AI leaving up to 68% of its lifetime budget unspent before the pacing fix landed.

Balance testing: both seats play as real AI, not a naive strategy

mobile/balance-sim.js is the tool for politician/agenda balance questions — every politician as P1 against every other politician as P2, both sides driven by the actual AI (Game.setupAI(game, playerKey, rng) + Game.runAIFull(), so a new playerKey/oppKey parameter on aiStep/runAIFull and their scoring helpers no longer hardcodes 'p2'), logged to mobile/balance-log.jsonl across N seeds per ordered pair. Read win rate as the primary metric, not average final seats — a hung parliament counts as a 0.5/0.5 draw in the tally, matching the game's own rule, and avg seats doesn't map cleanly onto how often a kit actually wins. A 1,260-game batch confirmed Rahul Gandhi, Mamata Banerjee, and Manmohan Singh as genuinely bottom-tier (avg final seats 172.5 / 170.7 / 196.5 vs. Hema Malini's roster-best 261.7), each for a different structural reason — see findings.md. Re-run after any politician/agenda tweak (node mobile/balance-sim.js 5, higher for more confidence).

The project convention after touching AI aggressiveness specifically is to also stress-test cheap/tiny states directly, not just run the normal suite — a more aggressive AI can drive a state to exactly 100% for the first time, which is exactly how a real zero-denominator bug in loseAt() was caught before.

npm test alone won't catch a duration/timing bug — write a diagnostic script that exercises the real sequence

Modi's Demonetization (a one-phase funds freeze) shipped with an off-by-one: fundsFrozenUntilPhase = game.phase + 1 instead of game.phase, which let the AI opponent invest/tap normally for the rest of the phase the power was used in, before the freeze actually bit the following phase — the opposite of "one phase" as advertised. Neither npm test script would ever exercise this, since neither activates a power mid-phase and then checks whether the very next action in the same phase is blocked. Found 2026-07-28 by a small standalone script directly calling investCash/tapAgenda/aiStep around the activation point. General rule for any one-phase-duration power: the expiry field must be set to the current game.phase at activation, never +1 — the effect self-clears the moment game.phase moves past it, which requires it to already be active during the activation phase itself.

Balance conclusions need an isolated re-test, not a before/after full-batch diff

Comparing mobile/balance-sim.js win rates across two full batch runs where other politicians' data also changed is confounded by "strength of schedule" — a nerf can appear to backfire (win rate goes up) purely because 2–3 of that politician's 20 simulated opponents got weaker in the same batch. Toggle one politician's data, hold every other politician at the exact same committed state, and re-run before trusting a specific before/after comparison.
