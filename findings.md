## 2026-07-24 — Recomputing the Plausibility-check table against the real 30,000 Cr budget reverses the design doc's "cash alone can never win" claim
**Finding:** At the new budget, the idealized cash-only scenario (no tokens, no agendas, opponent passive, spend spread evenly) clears 272 seats on its own: ~281/543 (51.8%), a ~9-seat margin — versus the old budget's ~203/543 (37.4%), well short of a majority. The combined-strategy margin (cash + full tokens + 2 strong agendas) widened from ~19 seats to ~99 seats over 272.
**Context:** Verified the recompute methodology first by reproducing the design doc's own pre-existing ~203/543 and ~42-seat figures exactly (bit-for-bit) using the same round-cost/decay-curve formula (`costPerTap = seats×10`, boost decaying 500→200 bps over 20 taps, one "round" = tapping every one of the 543 seats once at a flat 5,430 Cr), then applied the identical method to the new 30,000 Cr budget.
**Implication:** The design doc's "cash alone still cannot win under any circumstances — a hard mathematical wall" framing is no longer accurate and has been corrected. More importantly, the unmodeled "two-active-player" case (a real adversarial opponent contesting the same states, not the passive-opponent idealization used throughout this section) is now the single most load-bearing open question in the document — a ~99-seat idealized cushion says much less about real-match balance than the old ~19-seat one did, and is worth prioritizing before further economy tuning.

## 2026-07-23 — "Modi's home-state bonus isn't working" was the documented shared-home-state tie rule, not a bug — Sardar Patel also has homeState "Gujarat"
**Finding:** User reported Narendra Modi starting at only 25% popularity in Gujarat at phase 1, suspecting the home-state bonus was broken. Direct simulation of `generateStartingPosition` confirmed the bonus code works correctly in general (Modi's Gujarat share was always ≥30% across 10 trials against various opponents — matching the documented "+25% on top of baseline roll" floor). Simulating Modi vs. Sardar Patel specifically (the one other roster politician whose `homeState` is also "Gujarat") reproduced exactly 25% in 2 of 8 trials — matching the user's report precisely.
**Context:** Found by testing the starting-position generator directly with real game data rather than re-reading the (already-correct) bonus code; the roster check (`data/politicians-data.json`) showed Modi and Sardar Patel are the only two of 20 politicians sharing Gujarat as home state.
**Implication:** This is the existing documented tie rule working as intended (`design/economy-status-map.md`'s Home state section: shared home state → bonus nullified for both, no split) — no code change was made. Worth remembering Modi/Patel as the concrete example next time a "home bonus isn't applying" report comes in: check whether the AI opponent that match happened to share the same home state before assuming a code bug.

## 2026-07-23 — mobile/sw.js's cache-first fetch strategy meant a phone's cached build never picked up code changes until the service worker's own bytes changed
**Finding:** The `fetch` handler did `return cached || network` — always serving a cached response first if one existed, and only updating the cache in the background for *next* load. Combined with a static cache name (`pme-mobile-v1`), and browsers only re-running a service worker's `install` when the *byte content of `sw.js` itself* changes, a phone that had cached the build once stayed permanently stuck on that version regardless of what was actually on the server.
**Context:** User reported the AI still showing pre-fix fund behavior (starting at 0, no phase refresh) despite the source already being corrected in `mobile/game.js`. Traced by reading `sw.js` directly rather than re-debugging the already-fixed game logic.
**Implication:** Fixed to network-first (`fetch` preferred, cache only as an offline fallback) and bumped the cache name to force a clean slate. Any future report of "the phone shows old behavior despite the source being fixed" on this project should check `mobile/sw.js`'s fetch strategy and cache version first, not re-debug the already-fixed code.

## 2026-07-23 — The apparent "AI always has ~0 funds" complaint was not a funds-refresh bug — both players get identical funds, the AI just spends its entire pool down to near-zero every phase before the player's first render
**Finding:** Instrumented `createGame`/`startPhase` directly: `startingFundsCr:2500 + fundsRefreshPerPhaseCr:1000` gives both p1 and p2 exactly 3500Cr at phase start. But `runAI()` (at the time) ran synchronously inside `startPhase()`, and its last step looped buying seat-investment until funds dropped below `costPerSeatCr` — so by the time the UI rendered, p2's funds were already spent to ~0, every single phase, by design (a greedy heuristic), not because refresh was broken.
**Context:** User suspected either a leftover economy bug or "the AI just plays too fast" — this trace confirmed the latter and ruled out the former before any code changed.
**Implication:** Motivated the pacing rework (aiStep()/runAIFull() split, ~20 actions/min throttle in main.js) — the actual fix was behavioral/pacing, not an economy-engine correction. Confirms `startPhase()`'s funds-refresh logic itself is symmetric and correct.

## 2026-07-23 — mobile/index.html has no `<meta name="viewport">` tag at all
**Finding:** Grep and a direct `<head>` read confirmed zero viewport meta tag. Under Playwright/webkit with `devices['iPhone 14']`, `window.innerWidth` measured 980 (the classic no-viewport-tag Safari fallback canvas) even when the browser context's own viewport was explicitly forced to 390×664 — the page's CSS layout viewport ignores emulated/physical width entirely without the tag. Only injecting a viewport meta tag via response-body route interception (test-only, not applied to the real file) produced a true 390px layout render.
**Context:** Discovered while verifying whether a new 7-button action row would wrap at real iPhone width, during the "combined action bar" iteration of the corner-buttons redesign.
**Implication:** Not fixed — out of scope for the requesting task, and the user's real device apparently renders it acceptably regardless (confirmed via their own screenshot showing normal proportions). Flagged to the user directly. This project's CLAUDE.md already documents the *prototype* (`pme-mobile-sheet.html`) intentionally omitting this tag for chrome-height reasons; `mobile/index.html` (the real build) has the same omission and it's unclear whether that's deliberate or inherited by accident — worth revisiting if iOS-specific zoom/scaling issues are ever reported.

## 2026-07-23 — AI investment scoring used raw boost/cost with no regard for remaining headroom, so the AI would endlessly reinvest in an already ~100%-owned state instead of moving to the next state in its target group
**Finding:** `scoreInvestState()`'s formula (`boost/cost + tiebreaker`) always favored the cheapest state in a group regardless of how close that state already was to full ownership, since `investCash`'s actual gain caps at `10000 - currentShare` but the score never accounted for that cap. Stress test with unlimited funds (3000 forced `aiStep()` calls): before the fix, the AI stayed stuck on group index 0 for all 2982 successful investment actions and 0 of 15 regional-dominance groups reached full dominance. After changing the score to use effective remaining headroom (`min(boost, 10000-currentShare)/cost`) instead of raw boost, the same test reached full dominance in all 15 groups within 911 actions.
**Context:** Found while stress-testing the newly-added group-based AI investment targeting (round-robin over `game.groups`, skipping already-dominant ones) — the grouping alone didn't produce the intended "invest across the group" behavior until this scoring fix.
**Implication:** This was a real, previously-undetected inefficiency in the investment AI (pre-existing before the group-targeting change, just newly exposed by it) — worth remembering if investment-AI scoring is touched again. The fix is in `mobile/game.js`'s `scoreInvestState()`.

## 2026-07-23 — `.vs-bar[hidden]` did nothing because `.vs-bar{display:flex}` (author CSS) beats the browser's default `[hidden]{display:none}` UA-stylesheet rule at equal specificity
**Finding:** Setting `$('cardVsBar').hidden = true` in JS left the vs-bar still visibly rendered underneath the new group-card LED grid, confirmed via a Playwright screenshot. This codebase already has the fix pattern established in three other places (`.overlay[hidden]`, `.group-readout[hidden]`, `.target-banner[hidden]`) — it was simply missing for the newly-added `.vs-bar`.
**Context:** Found while visually verifying the new group-overview card feature (LED indicators per state in a group) — the vs-bar (only meaningful for a single selected state) should have been replaced by the LED grid but wasn't disappearing.
**Implication:** Fixed by adding `.vs-bar[hidden]{display:none}`. This is now a 4-instance pattern in this codebase: any element toggled via the `hidden` attribute must get an explicit `<selector>[hidden]{display:none}` rule if that same selector's base class already sets its own `display` value — proposed as a CLAUDE.md rule (see checkpoint).

## 2026-07-23 — engine.js's loseAt() let a popularity loss vanish when a player held exactly 100% of a state, breaking the p1+p2+others=10000 bps invariant
**Finding:** When `self` (a player's share of a state) is exactly `BPS` (10000) — reachable by tapping a cheap 1-seat UT enough times — `opponent` and `others` are both 0, so `loseAt()`'s `if (denom > 0)` guard skipped the split entirely, leaving `oppGain`/`othGain` at 0 while still unconditionally doing `pop[actor] -= loss`. The freed share disappeared instead of landing anywhere. `gainAt()` has no equivalent bug because a `self`-at-cap boost is clamped to `gain=0` before the same-shaped branch is ever reached — only the loss path has this asymmetry.
**Context:** Surfaced only after adding 4 AI personality profiles (task: "AI difficulty/personality variety") — the `aggressive-investor` profile taps agendas less and invests far more, which was the first thing to actually drive a tiny cheap state to 100% ownership and then apply a negative agenda effect there within the 6-phase power-activation test window. Confirmed via a targeted trace script showing `INAN`/`INLD`'s pop sum shrinking by exactly the agenda's per-tap delta each phase while `p1`/`others` stayed frozen at 0.
