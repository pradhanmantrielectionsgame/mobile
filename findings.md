## 2026-07-28 — Changing `game.winner` alone wasn't enough to make hung parliament read as a draw — the end screen had its own independent, redundant check
**Finding:** `mobile/main.js`'s `showEndOverlay()` computed its hung-parliament headline from `var vsAI = game.players.p2.isAI; headline = vsAI ? 'Hung parliament — you lose' : 'Hung parliament';` — it never actually read `game.winner` for this branch, it independently re-derived the same "AI wins ties" conclusion ADR-0006 encoded in `finalizeGame()`. Fixing `finalizeGame()` alone (setting `game.winner = 'draw'` unconditionally) would have left the end screen still showing "you lose" on every hung parliament, since this UI code path never consulted `game.winner` in the first place.
**Context:** Found while implementing ADR-0010 (hung parliament is always a draw, superseding ADR-0006) — a grep for `vsAI`/`isAI` in `main.js` turned up the duplicate logic before it shipped as a silent regression.
**Implication:** When changing what a `game.winner`/game-state outcome means, grep for every place that independently re-derives the same conclusion, not just where `game.winner` itself is read — this project has hit this "two places must agree" failure mode repeatedly (CLAUDE.md documents several: agenda effect text vs. real benefits/costs, the `[hidden]` CSS attribute rule, etc.) and this is another instance of the same pattern.

## 2026-07-28 — `balance-sim.js`'s reported win rates were almost entirely a measurement artifact: 76% of games hit a hung parliament, and the game's own tie-break rule always awarded it to p2
**Finding:** Checking the existing `mobile/balance-log.jsonl`, 1,595/2,100 games (76.0%) ended in a hung parliament (neither side reached the 272-seat majority). The real game's own rule (`finalizeGame()`, ADR-0006) resolves a hung parliament as `game.winner = game.players.p2.isAI ? 'p2' : 'draw'` — correct for a human-vs-AI match, but in every simulated game p2 was always the AI slot, so p1 (whichever politician was being measured) structurally lost 76% of games by rule alone, regardless of kit quality. This was a far bigger driver of the near-0% win rates across most of the roster than the naive-p1-vs-full-AI-p2 strategy gap that was initially suspected.
**Context:** User asked "how can the win rate for so many be 0 percent" after a first re-ranking by win rate (not avg seats, per user's correction) showed 13 of 21 politicians at 0-3%.
**Implication:** Any future win-rate measurement from this simulator must either (a) treat hung parliament as a neutral outcome (this session scored it 0.5/0.5 in `balance-sim.js`'s own tally, without touching the real game's ADR-0006 rule) or (b) explicitly account for its ~76-95%-per-politician frequency before drawing conclusions from a raw win/loss count.

## 2026-07-28 — `mobile/game.js`'s AI logic (`aiStep`/`runAIFull` and their scoring helpers) was hardcoded to player key 'p2' throughout, not just at the top level
**Finding:** Beyond the previously-known `aiStep`/`runAIFull` hardcoding, the helper functions they call — `pickAIPowerTarget`, `pickAICompletedAgenda`, `groupFocusBonus`, `scoreInvestState`, `bestInPool`, `pickAIInvestmentTarget` — all had 'p1'/'p2' literals baked into their logic (e.g. `scoreInvestState`'s tie-break term was hardcoded `game.pop[s.svgId].p1 - game.pop[s.svgId].p2`, assuming the actor is always p2 and the opponent always p1). All were generalized to take explicit `playerKey`/`oppKey` parameters, with `aiStep`/`runAIFull` defaulting `playerKey` to `'p2'` so every existing call site (`main.js`, `simulate.js`, which never pass a second argument) behaves identically to before.
**Context:** Needed to let `mobile/balance-sim.js` drive p1 with the real AI too (a symmetric AI-vs-AI match), rather than the naive/random strategy it used previously — the project's own prior finding had flagged the object-swap approach as unsafe but hadn't yet built the proper generalized version.
**Implication:** A new `Game.setupAI(game, playerKey, rng)` export now flags an arbitrary seat as AI-controlled (profile + target group), matching what `createGame` already did for p2. Any future headless test needing a second AI-controlled seat should use this rather than reinventing naive-strategy stand-ins.

## 2026-07-28 — A power-magnitude nerf can appear to backfire when compared across simulation batches where other politicians' kits also changed ("strength of schedule" confound)
**Finding:** Cutting Hema Malini's power from 8%/16% (nationwide/home) to 2%/16% appeared to raise her measured win rate from 60.0% to 64.5% in a batch where 2-3 of her 20 simulated opponents (Sivaji Rao, Rajinikanth) were also weakened in the same run. Re-testing with her power alone toggled, opponent pool held exactly constant, showed the true effect was a genuine -13-point drop (77.5% with the old power → 64.5% with the new one) — the batch-level comparison had been confounded by her opponents getting weaker at the same time.
**Context:** User pushed back that the result "makes no sense" for a change that was strictly weaker in every state except an unchanged home bonus.
**Implication:** Any future single-politician balance change should be verified with an isolated test (only that politician's data toggled, everyone else held at the current committed state) before trusting a before/after comparison across two full batch runs, since `balance-sim.js`'s win rate is relative to the whole 20-opponent pool, not an absolute measure of one kit.

## 2026-07-28 — A magnitude-only nerf hits diminishing returns; breaking through required combining it with a much later `requiresMinPhase` gate in the same edit
**Finding:** Cutting Amitabh Bachchan's "Celebrity Endorsement" nationwide magnitude from 12%→10% dropped his win rate 78%→71% (-7pts), but the next equal-sized cut (10%→8%) only moved it 71%→67.5% (-3.5pts) — diminishing returns on the same lever. An earlier attempt to fix him via cost+timing alone (₹1,000cr→₹2,000cr + `requiresMinPhase: 3`, magnitude unchanged at 12%) moved his win rate by exactly 0%. The combination that finally broke through was magnitude 8%→6% **together with** pushing `requiresMinPhase` from 3 to 6 in the same edit, dropping him 67.5%→62%.
**Context:** User's target was closing the gap between Bachchan and the rest of the top cluster (Rajinikanth 58.5%, Hema Malini 60%) without eliminating his "hardest to beat" status entirely.
**Implication:** For this politician's specific power shape (nationwide, "Others"-sourced, no per-region interaction), a single lever pushed further has diminishing effect — a small early-gate `requiresMinPhase` value (3, i.e. usable almost immediately) contributes far less than a late-game one (6, roughly the midpoint of the 10-phase match) since it cuts off several extra phases of compounding benefit. Test cost/timing/magnitude changes in combination, not just escalating one lever repeatedly, if an earlier single-lever version underperformed expectations.

## 2026-07-28 — The existing single-player engine architecture is already well-shaped for real-time human-vs-human networking, with almost no engine changes needed
**Finding:** `mobile/game.js`'s action functions (`investCash`, `playRallyToken`, `tapAgenda`, `activatePower`, etc.) are already pure, side-effect-free, playerKey-agnostic mutators — `(game, playerKey, ...args) → {ok, reason?}`, no DOM/sound/console access. The AI opponent (`aiStep`) is not a separate code path; it calls these exact same functions with `playerKey='p2'`. Separately, `mobile/engine.js`'s `resolveSimultaneousGain` already exists specifically to reconcile two players' actions landing on the same state in the same phase — the engine already assumes concurrent two-sided play, it has just never been fed by a second live human player.
**Context:** User asked how to extend the game to real-time 2-player-over-internet play. A research pass over `game.js`/`main.js`/`engine.js` (plus pre-existing ADR-0001/0002/0007 on deferred live matchmaking) found these properties already in place rather than needing to be designed from scratch.
**Implication:** A networked multiplayer layer can be built as an additive `mobile/net.js` module that publishes/replays actions through the existing `G.*` functions (an event-sourced action log), without modifying `game.js`/`engine.js` internals. Full architecture written to `design/multiplayer-implementation-plan.md`. The one real gap is determinism: `game.rng` is currently seeded with unshareable `Math.random` and needs a swappable seeded PRNG for two clients to reach identical starting positions.

## 2026-07-28 — Starting-position seat variance: the stopping-rule threshold controls the mean without widening the spread
**Finding:** `mobile/engine.js`'s `generateStartingPosition()` (pre-fix) produced starting national seats averaging ~135-142 with a right tail reaching 180-200+ for one player — confirmed via 3,000-8,000-sample direct simulation, with ~46-47.5% of games putting at least one player over 150 seats (not a rare tail, close to a coin flip). Raising the advantage-draw stopping threshold (`drawStopAt`/`drawBudget`, 100/130 → 124/154) shifted the mean up to ~150 while leaving the standard deviation essentially unchanged (~12.4-12.7 across the whole tested range) — because the stopping rule is self-correcting: a player who draws a run of small states just needs more draws to cross the threshold, which keeps the overshoot (and therefore σ) stable regardless of where the threshold sits.
**Context:** User reported seeing 180-200-seat starts in actual play and initially proposed narrowing the baseline population range (500-2900 bps) as a fix; a parameter sweep showed narrowing the baseline instead just drags the average down without independently controlling the tail. Direct mean/σ measurement (not inferred from percentiles) was needed to find that the advantage-draw threshold is the one knob that moves the mean without stretching the spread, letting a plain reject-and-retry hard cap (tried first) be replaced with pure parameter tuning once the user's actual target — mean 150, σ~12.5 (175/125 as 2σ events) — was made precise.
**Implication:** Any future tuning of this generator should be checked via direct mean/σ simulation, not intuition about which knob "should" raise or lower the total or its spread — several knobs (`baseHi`, `drawStopAt`, `advHi`) all move the mean, but only empirical measurement revealed which one leaves σ untouched.

## 2026-07-28 — Rahul Gandhi, Mamata Banerjee, and Manmohan Singh are empirically the weakest politicians in the 21-politician roster, each for a different structural reason
**Finding:** A 1,260-game batch simulation (`mobile/balance-sim.js`, every politician as p1 with a fixed naive strategy vs. every other politician's real AI as p2, 3 seeds/ordered pair) showed Mamata Banerjee (avg final seats 170.7) and Rahul Gandhi (172.5) as the two worst performers in the roster, with Manmohan Singh (196.5) also bottom-tier — versus e.g. Hema Malini's 261.7. Root causes differ per politician: Manmohan Singh's own special power (Economic Reform) costs -8% popularity in AgriculturalRegion states, which includes his own home state Punjab — a direct self-inflicted tax on his own base, compounded by 3 of his 4 agendas being net-negative on Punjab's own tags. Rahul Gandhi's 4-agenda kit nets slightly negative (-8bps) on his own home state Uttar Pradesh, driven mainly by Secularism's -12/-12 HindiHeartland/Pilgrimage penalty landing on his own turf; UP is also shared as "home" by 8-9 of 20 politicians, so the home-bonus-nullification rule triggers against him unusually often. Mamata Banerjee's home-state popularity is actually healthy (~66% at game end, uncontested West Bengal) but 3 of her 4 agendas (State's Rights, Secularism, Agricultural Reforms) are net-negative across Hindi Heartland/Industrial Corridor states — the country's largest seat blocs — with no offsetting positive-nationwide agenda in her kit.
**Context:** User asked for a thought experiment on why certain politicians felt harder to win with, based on a small manual-play sample. Investigated by hand-computing tag-effect arithmetic per politician's home state against `data/policy-tags.json`/`data/states_data.json`, then building `mobile/balance-sim.js` to get a real empirical sample rather than relying on the small manual sample alone.
**Implication:** `mobile/balance-sim.js` is now available as a repeatable tool for future politician-balance work — rerun after any politician/agenda tweak (`node mobile/balance-sim.js 5` or higher for more confidence) rather than relying on manual small-sample play. No politician rebalance was implemented this session, only the measurement tooling and the diagnosis.

## 2026-07-28 — Modi's Demonetization froze the opponent's funds a full phase late — an off-by-one that directly contradicted the design doc's own explicit ban on delayed-trigger power effects
**Finding:** `mobile/game.js`'s `activatePower()` set `who4.fundsFrozenUntilPhase = game.phase + 1` when applying the `freezeFunds` benefit, so `fundsFrozen(pl, game)` (`pl.fundsFrozenUntilPhase === game.phase`) stayed false for the entire phase the power was activated in — the AI kept investing/tapping normally right after the user used it, only actually freezing the *following* phase. `design/economy-status-map.md` (revised 2026-07-26, the same day Demonetization shipped) explicitly bans this exact pattern: "resolves on a delay (e.g. 'triggers at the start of the next phase')" is called out as banned, with one-phase effects required to "self-clear the moment `game.phase` moves past it" — i.e. apply immediately.
**Context:** User reported "the AI can still click around and I can visually see the funds being deducted for each click" right after activating the power. A diagnostic script (`Game.createGame` + directly calling `investCash`/`tapAgenda`/`aiStep` on the real `mobile/game.js`/`engine.js`) proved the mechanic's gating logic itself was correct in isolation (blocks funds spend exactly during the flagged phase) — the bug was which phase got flagged.
**Implication:** Fixed by setting `fundsFrozenUntilPhase = game.phase` (not `+1`) — the freeze now lands the instant the power activates and expires automatically once the phase advances. Any future duration-based special power in this project must set its expiry field to the *current* `game.phase`, never `+1` — check this specifically against `design/economy-status-map.md`'s explicit delayed-trigger ban whenever a new one-phase-duration power is added.

## 2026-07-28 — Only 6 of 20 politicians have a dedicated power-sound file; the missing-file fallback silently undid background-music ducking for the other 14
**Finding:** `playPowerSound()` (`mobile/main.js`) ducks `bg_music` to volume 0 before playing a politician's `sounds/<Name>.mp3` clip, but its `.catch()` fallback (for the 14/20 politicians with no dedicated file) reset `bg_music.volume` back to full *before* playing the generic `fanfare` sound — undoing the duck right when the fallback needed it most, so fanfare played over full-volume music. Separately, even for politicians *with* a dedicated file (e.g. Rajinikanth), the clip itself was mastered too quietly to hear clearly even with music fully muted — `HTMLAudioElement.volume` caps at 1.0, leaving no headroom to compensate.
**Context:** User reported special-power audio "drowned out by background music" for a politician without a dedicated file, then reported the same for Rajinikanth (who has one) after the fallback fix — the ducking mechanism was confirmed working correctly via design-doc/code cross-check; the actual issue was the clip's own quiet mastering.
**Implication:** Fixed the fallback to keep the duck applied through the fanfare fallback too (restore only fires once whichever sound actually finishes). Added a shared Web Audio `GainNode` (2.5x boost, `mobile/main.js`) on all power-sound playback to push past the `.volume` ceiling for quiet clips — one flat boost across all clips since there's no way to listen and calibrate per-file in this environment; revisit if a specific clip starts sounding distorted/clipped.

**Finding:** All three HTML files load the same shared `engine.js`/`game.js`/`main.js`, but each has its own fully-duplicated `<style>` block rather than a shared stylesheet. **Context:** User reported "I don't know if you applied any change... I didn't see any flashy animation" twice in a row. **Implication:** Any future CSS-only change to support a shared JS behavior (a new fx/animation, a newly-toggled-visible element, etc.) must be applied to all three HTML files' `<style>` blocks, not just `mobile/index.html` — this is the same "shared JS, unshared markup" trap already documented for `mobile/manifest.json`'s `start_url` in CLAUDE.md, just hitting `<style>` blocks instead of manifest links this time.

## 2026-07-27 — This app's own established Playwright viewport convention (980×2130) only matches real Safari with browser chrome hidden; a normal tab gives ~462px less usable height, hiding real overflow bugs
**Finding:** The project's documented headless-testing convention for this no-`<meta viewport>` app is `viewport:{width:980, height:~2130}`. That figure matches real iOS Safari only when the address bar/toolbar are NOT visible (home-screen-installed or scrolled-to-hide). A separate, already-documented finding says real Safari with chrome visible gives ~664px usable CSS height, not 844px — scaled into this app's ~980px-wide fallback canvas (980/390×664), that's ~1669px, not ~2130px. Testing `index-redesign-a.html`'s politician-select cards at 980×2130 showed 0px overflow for all 21 politicians; re-testing at 980×1669 (the real worst case) showed every card overflowing 187-327px, with Nehru/Ambedkar/Modi/Indira Gandhi worst — exactly matching a user bug report.
**Context:** User reported Modi, (Indira) Gandhi, and Nehru's politician-select cards were visibly cut off on their phone, despite an initial self-check claiming a clean fit.
**Implication:** Any future headless "does this fit / does this overflow" self-check of this app's full-screen overlays must test at BOTH the generous ~2130px canvas height AND the real chrome-visible ~1669px height — the smaller one is the actual worst case for anyone using a normal (non-installed) Safari tab, and the 2130px figure alone can hide real, user-visible overflow bugs.

## 2026-07-27 — `object-fit:cover` has no single crop anchor that works across a set of illustrations with varying composition; `object-position` tuning that fixes one image breaks another
**Finding:** Fixing the politician-card overflow above required shrinking the (previously fixed-height) portrait region to a flexible, content-driven size. With `object-fit:cover` and default centered crop, this cut off Nehru's cap (subject positioned high in frame). Switching to `object-position:50% 0%` (top-anchored) fixed Nehru but then cropped Modi's face out entirely, since Modi's illustration has his face lower with a raised fist above it — different politicians' portraits have different subject placement, so no single crop anchor serves all of them.
**Context:** First attempt (object-position:top) was shown to the user as fixed; user immediately flagged it still looked broken, pointing at a different politician's card.
**Implication:** For any image set with inconsistent internal composition (not just this politician roster — any future art batch), don't try to find one `object-position` value that works for all of them. ## 2026-07-23 — Seat-conversion rounding (state seats = round(popularity% × seats)) can over-allocate a state's total seats
**Finding:** Computing each player's seat share independently via plain rounding has no reconciliation step, unlike bps popularity redistribution (which guarantees the three shares always sum exactly). Worst case demonstrated: a 3-seat state at P1 50% / P2 25% / Others 25% gives exact quotas of 1.5 / 0.75 / 0.75 — independent rounding gives 2 / 1 / 1, handing out 4 seats from a state that only has 3.
**Context:** Found during a requested structural review of `design/economy-status-map.md`, by analogy to the redistribution engine's own "round one side, derive the other" discipline — the seat-conversion step never got the same treatment.
**Implication:** Fixed by switching to largest-remainder apportionment (Hamilton's method): give each side `floor(quota)` first, then hand out the state's leftover seats one at a time to whoever has the largest fractional remainder. Now documented with pseudocode and a worked example in the Core loop section. Should be re-validated against the plausibility-check seat totals once implemented, since it can shift exact seat counts in edge cases (though not the shape of the ~19-seat passive-opponent margin finding).
