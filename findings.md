# Findings

## 2026-09-01 — An AI targeting function returning argmax over a *shared* resource is both predictable and quietly unfair to the human
**Finding:** `pickDisciplinedRallyTarget` (`mobile/ai.js`) sorted open states by seats and returned `pool[0]`, the single largest. Since every ladder rung from level 2 up carries `tokenDiscipline`, **every AI above the easiest one rallied Uttar Pradesh in every game**, then Maharashtra once UP hit the play cap — fully deterministic, never varying by politician, seed or phase. Two distinct problems, and the second is the one that isn't obvious from reading the function: `game.cfg.rally.maxPlaysPerStateShared` (2) is a **shared** cap across both players, so a bot that always takes the biggest state doesn't merely play predictably, it *consumes the human's access* to the best rally targets before the human can reach them. Replaced with a seat-weighted random draw over the states that clear the same economic bar (`weightedRallyPick`): a rally's value scales linearly with seats, so weighting by seats tracks the real payoff instead of discarding it. Measured over 40 games at level 8: **16 distinct states rallied, top two down to 13.8% each** from effectively 100%.
**Context:** Reported by the user from live play — "the stronger AIs place rally tokens predictably in the largest states UP, Maharashtra etc… it's also boring to play against them… It also robs you from holding rallies there." Both halves of that report were confirmed exactly in the code on first read.
**Implication:** Whenever an AI selection function picks a target from a pool the human also draws from under a shared cap, argmax is the wrong shape regardless of how correct its scoring is — prefer a value-weighted random draw, which preserves most of the expected value while leaving the contested resource genuinely contested. Audit the other pickers on this basis: `pickAIPowerTarget` still returns a strict argmax, though it competes for no shared cap. This is a *fairness/fun* axis that no strength metric will ever surface, since a stronger-but-boring bot scores better on every seat-margin measurement.

## 2026-09-01 — Randomising the AI's rally target cost nothing measurable and made the ladder strictly monotone
**Finding:** Re-running the full round-robin (`node mobile/ladder-sim.js 20`, 2,240 games) after replacing the rally argmax with a seat-weighted draw shifted every rung's margin down slightly — level 1 −101→−115, level 8 +180→+175 — while leaving the ordering completely intact. The monotonicity check went from two violations in the earlier 10-profile field to **passing outright: every rung beats the rung below it.** Current ladder: −115, −78, −60, −40, −10, +43, +86, +175 (± 6–11). Level 7→8 remains the one step inside noise (67 ± 38).
**Context:** Run in the background immediately after the rally change specifically to price it, on the assumption that deliberately weakening the bot's target selection would cost real strength.
**Implication:** A seat-weighted draw over an economically-screened pool is close to free relative to argmax, because expected value under linear-in-seats scoring is preserved by the weighting itself — so variety and unpredictability can be bought cheaply in this engine. More generally: price a "make it less optimal" change with the harness before assuming it costs strength; the intuition that any deviation from argmax must weaken the bot was wrong here.

## 2026-08-31 — `scripts/deploy-mobile.js` silently omitted `ai.js`, so the shipped game would have had a dead AI
**Finding:** The deploy script copies an explicit, hand-maintained file list (`copyTransformed`/`copyVerbatim` calls in `main()`), and `mobile/ai.js` was never added to it after the v2.4.0 AI-module extraction. A deploy would have shipped an `index.html` whose `<script src="./ai.js">` 404s, leaving `window.PMEAI` undefined — the game boots and the map renders, but `game.js`'s `ai()` lookup fails and the opponent never takes a single action. Caught only by checking the script's file list before pushing; nothing in `npm test` or the local dev server can see it, because both read from `mobile/` where the file exists. Also confirmed in passing that the live site was still on **v2.3.4** — v2.4.0 was committed but never deployed, which is the only reason this never shipped broken.
**Context:** Found while preparing the v2.5.0 deploy, following CLAUDE.md's existing standing instruction to dry-run `stripRelativePaths()` before pushing. That check passed; the missing-file problem was a separate one noticed while reading the same function.
**Implication:** The deploy file list is a manual allowlist that no test covers — **any new file added under `mobile/` must be added to `scripts/deploy-mobile.js`'s `main()` in the same commit**, or it silently vanishes from the live build. Add this to the pre-deploy check alongside the `../` dry-run: diff the set of `<script src>`/`<link href>` references in `mobile/index.html` against the script's copy list.

## 2026-08-31 — The app's global `touch-action:pan-x pan-y` silently breaks any `<input type="range">` on touch
**Finding:** `mobile/index.html`'s global rule `*{... touch-action:pan-x pan-y}` — added 2026-08-24 to block pinch-zoom during fast play — also makes the browser claim a horizontal drag on a range input as a pan/scroll gesture, so the slider thumb never moves on a touchscreen. The fix is `touch-action:none` on the range input specifically, which is scoped and does not reintroduce pinch-zoom anywhere. Note this class of bug is invisible to a Playwright check that sets `.value` and dispatches an `input` event programmatically (as this session's verification initially did) — that path never exercises the touch gesture at all.
**Context:** Hit while replacing the settings difficulty picker with a slider. Anticipated from the existing CLAUDE.md note about the global rule rather than discovered from a failure report, and applied pre-emptively.
**Implication:** Any future draggable control (range input, custom swipe handle, carousel built on pointer events) needs its own `touch-action` override against that global rule — and verifying it needs a real touch drag (`page.touchscreen`/real device), not a synthetic `.value` assignment.

## 2026-08-31 — Full AI round-robin tournament: 2,700 games, eight cleanly separated difficulty rungs
**Finding:** `node mobile/ladder-sim.js 30` ran every AI profile against every other, 60 games per pairing (45 pairings), mirrored so each matchup is played twice with the same two politicians in the same two seats and the bots swapped. Mean seat margin vs the whole field, weakest first: **easy −100.8 ± 4.4, medium −95.9 ± 4.1, hard −61.2 ± 4.8, expert −42.6 ± 4.4, cap0 −31.4 ± 5.2, regional-2 −22.3 ± 5.9, cap1 +10.2 ± 5.7, cap2 +55.1 ± 5.7, cap4 +108.7 ± 6.4, max +180.2 ± 7.8.** Every step exceeds its error bar except two: `medium` is genuinely *weaker* than `easy` (−14.4 ± 7.2, the unfixed agenda-amortisation bug), and `cap4` vs `max` is unresolved (49.3 ± 34.0 — they may be the same strength). `cap0` also loses to `regional-2` (−20.0 ± 7.7), so those two are out of order.
**Context:** Measured after `profile.groupCap` was added as the dial across the old 147-seat cliff between the weak rungs and `max`. Runtime ~4m15s for the full 10-profile matrix. A 12-seed run (1,080 games) 20 minutes earlier produced the same ordering and margins within noise, so 30 seeds is comfortably past the point where more games change the answer.
**Implication:** The ladder is real and usable: dropping `medium` and `cap0` (the two that break monotonicity) leaves eight strictly-ordered rungs spanning ~281 seats — easy, hard, expert, regional-2, cap1, cap2, cap4, max. Re-run this after ANY change to shared `aiStep` logic, since ADR-0016 notes a shared-code change shifts every rung's margin at once. Use seed counts of 30+; 12 is enough for ordering but leaves the top two rungs indistinguishable.

## 2026-08-31 (later still) — Chain ablation credited a two-flag partnership to one flag, and group capture turned out to be an all-or-nothing snowball rather than a skill
**Finding:** Measuring the AI ladder by adding one capability flag at a time (ADR-0016's design) attributed a 147-seat jump entirely to `spreadInvest`, the last flag added, and made `smartGroupTarget` look worthless (+15 ± 10, inside noise). Both readings were wrong: the two flags do nothing apart and everything together. Mirrored 28-game measurements of groups captured — `expert` (group targeting, no fixed scorer) **2.4**, `regional-2` (fixed scorer, no live group targeting) **0.2**, `max` (both) **7.3** — show the interaction directly. The mechanism is an economy, not a skill: a captured group pays cash, which buys investment taps, which capture more groups. `max` makes **429** investment taps a game against `regional-2`'s **170**, on near-identical unspent cash (~5 Cr), purely because seven captured groups fund it.
**Context:** Built `mobile/ladder-sim.js` (mirrored-pair, seat-margin, full round-robin over AI profiles — `balance-sim.js` cannot measure profiles at all, since it never passes a profile to `setupAI` and aggregates on politician id). A user proposal for an intermediate bot that obsesses over 1–2 random groups was built and measured; it lands mid-field (beats `expert` by 36) but *widens* the gap to `max` to 225, because confining a bot to two groups is exactly what stops it capturing the seven that fund the snowball.
**Implication:** Never read a single-flag delta from a chain ablation as that flag's value — it is the value of that flag *given every flag below it*, and a partnership shows up entirely on whichever half was added last. Any ADR-0016 rung measurement needs the full round-robin matrix, and interacting flags need a solo-flag row to be attributable at all. Practically: the gap between the weak rungs and `max` is not a dial-able competence, because regional dominance requires *every* state in a group over 50% and so pays nothing until it pays everything. The working dial is `profile.groupCap` — capping how many groups a bot may hold throttles the compounding directly and produces evenly spaced rungs (measured overall margins: cap0 −31, cap1 +14, cap2 +55, cap4 +98, uncapped +178).

## 2026-08-31 (later) — `max` beat a human 374–142 on the first confirmed-build playtest, overturning the same day's "a human vetoes the group engine" finding
**Finding:** With the four shipped profiles commented out of `AI_PROFILES` so `max` was the only drawable profile — and the version label reading `v2.4.0+max` on the device that played it — `max` (as Rajinikanth) beat the user 374–142, taking **3 regional groups to the human's 0** and using its Nationwide Rally. The earlier same-day entry below, which recorded `max` taking **0 groups** and losing 196–288 against a human, was almost certainly measured against a shipped profile, not `max`: it predates the single-profile pool and relied on the `?ai=`/localStorage override plumbing that the first finding in this file documents as silently failing on the phone. Treat that entry's human-vs-`max` numbers as void; its bot-vs-bot measurements (7–9 groups, ~400 seats) and its mechanical account of *why* group compounding is vetoable both stand. **Superseded in part, same day — see the entry above this one: the group-compounding claim it made was right, and a later chain-ablation reading that appeared to refute it was itself the error.**
**Context:** Three of the four AI-ladder playtests on 2026-08-31 could not confirm which bot they played. The fix that finally worked was not better override plumbing but deleting the need for it — commenting out the other profiles so `pickAIProfile` has one possible return value, which no query string, service worker or storage quirk can defeat. The opponent drew Rajinikanth, the roster's acknowledged strongest kit, so the margin overstates the typical case; the group count does not, and that is the number the earlier entry got wrong.
**Implication:** A capability that can only be observed by playing a match should be isolated by *removing the alternatives*, not by adding a selector — a one-line comment-out is more trustworthy than any amount of override plumbing, and it fails loudly (wrong bot is impossible) rather than silently (wrong bot looks like a weak bot). Re-measure any human-vs-bot claim made before the single-profile pool existed. The ladder's group-veto concern is still open but is no longer supported by evidence.

## 2026-08-31 — Every URL- and localStorage-based playtest override failed on the real device; only a build marker rendered in the UI proved anything
**Finding:** Three successive mechanisms for forcing a specific AI profile during a playtest all failed on the user's phone while working end-to-end in desktop Chrome: `?ai=<key>`, `?p2=<politician id>`, and finally a tap-the-version-label toggle persisted in `localStorage`. Root cause never found. What *did* work was rendering the state into the UI: the version label now shows `v2.3.4+max` when an override is live, `+ai` when `mobile/ai.js` loaded but no override took, and plain `v2.3.4` on an old build — the user reported `+ai`, which localised the failure to the override plumbing in one message instead of another full match. Two playtests were spent before this existed, both misread as "the new bot is weak" when the new bot may not have been running at all. Also disproved along the way: the service worker is **network-first for JS** (`fetch(..., {cache:'reload'})` with a 3.5s timeout, `skipWaiting` + `clients.claim`), so a stale precache was never the explanation, contrary to an initial diagnosis.
**Context:** Two live playtests of the new `max` profile came back looking like ordinary shipped-AI games (0 regions dominated, no Nationwide Rally), with no way to tell whether the profile was actually in play. Resolved by driving the tunnel URL in desktop Chrome and reading `window.__game.players.p2.aiProfile.key` directly, which confirmed the override worked there.
**Implication:** Any behavioural change that can only be observed by playing a match needs a visible build/config marker in the UI *before* the first playtest, not after two inconclusive ones. Never diagnose "the AI played badly" from match stats alone until the build identity is confirmed on the device that played it. The eventual fix was to stop overriding at all and put `max` in the normal random pool, so no plumbing stands between the code and the playtest.

## 2026-08-31 — Fire-on-craft power timing lets a politician's own special power permanently disable its Nationwide Rally
**Finding:** `aiStep` activates a crafted special power on the very next tick, unconditionally — a rule inherited by the new `max` ladder profile. As **Sivaji Rao (Nayak)**, whose *One-Day Ordinance* costs "every future rally token you'd otherwise earn" (`tokenIncomeStopped`), the AI crafts the special around phase 2–3, fires it immediately, and thereby cuts off the token income it needs to ever reach the Nationwide Rally's 12-token craft cost. It trades ~16 future tokens — the whole Nationwide Rally plus change — for 100% popularity in one 48-seat state. Measured across the roster (8 seeds per politician, `max` in the p2 seat): Nayak `usedNationwide` **0%** / `tokenIncomeStopped` **100%**; Mamata Banerjee also **0%** but *not* token-stopped (a second, still-undiagnosed cause); every other politician **100%**.
**Context:** User playtested `max` in the browser via `?ai=max`, drew Nayak as the opponent, and reported the AI "hoarded tokens but didn't use nationwide at all" while feeling no harder than the shipped AI. Also confirmed in the same investigation that the browser's AI tick pacing is *not* a factor: replicating `planAITickPacing`'s exact budget (dry-run count, `phaseMs/count` clamped to 300–4000 ms) in a headless run produced results identical to unpaced play, 30 seeds, same seats/groups/nationwide rate.
**Implication:** Power timing is load-bearing for any bot that also wants the Nationwide Rally, not the optional polish item it was first filed as — a bot must not fire a power whose cost is *future* tokens until the nationwide rally is crafted or deliberately abandoned. Separately, a methodology note: one live playtest draws one random opponent, and this one happened to draw the single politician whose power self-sabotages. A single match can't distinguish "the AI is weak" from "this politician's kit self-destructs" — check the per-politician sim table before drawing either conclusion.

## 2026-08-31 — Regional-dominance compounding is the strong bot's whole edge, and a human vetoes it by holding one state per group
**Finding:** The `max` profile's strength comes overwhelmingly from group-payout compounding: in a traced game it spent **45,540 Cr against a 27,500 Cr baseline budget** (starting funds plus refreshes), the surplus being regional-dominance payouts at 5 Cr/seat instant plus 0.5 Cr/seat/phase held, recycled into more investment taps. Against the four shipped profiles it averages 7–9 groups and ~400 of 543 seats. Against a human playing an ordinary game it took **0 groups** and lost 196–288. Regional dominance requires *every* member state above the 50% threshold, so an opponent who holds a single state in each group switches the entire compounding engine off; the bot then runs on its investment lever alone, which converts at a flat ~200 Cr/seat.
**Context:** Built `max` as the ladder's top rung and measured it bot-vs-bot, then the user played it live and won comfortably while "playing pretty average" and forgetting their own Nationwide Rally.
**Implication:** Bot-vs-bot margins systematically overstate any group-dependent profile, because the thing that separates the rungs is exactly the thing a competent human neutralizes — the same trap already recorded on 2026-08-21 for conditional special powers, now with a second instance. The difficulty ladder cannot be calibrated from AI-vs-AI alone; a rung's rating needs at least a sanity check against real play. A group chase should also be robust to contest — sinking cash into a group an opponent can veto with one state pays nothing at all for the effort.

## 2026-08-30 — The engine's p1/p2 coupling is asymmetric: seat output already 3-way, action input rigidly 2-way
**Finding:** Grepping `mobile/engine.js` + `mobile/game.js` to cost out an "Others as a spending agent" feature: the seat-*output* path is already fully 3-way — `pop[svgId]` is `{p1,p2,others}` in bps everywhere, `apportionSeats()` and `nationalSeats()` split each state's seats across `['p1','p2','others']` with Hamilton's method (Others already wins ~70–99 of 543 seats per sim game), and `generateStartingPosition` starts Others as the largest bloc (~66% mean; `randInt(rng, 500, 2900)` per player, others = remainder). But the *action/input* path is rigidly binary: `otherPlayer(actor)` is `actor === 'p1' ? 'p2' : 'p1'`, wired into `gainAt`/`loseAt`/`resolveSimultaneousGain`/`computeScore`/the AI scorer; `startPhase` plus all three payout functions hard-code `['p1','p2'].forEach`; the whole action layer and `aiStep` assume the actor is p1 or p2. `gainAt` is commented in-file as "the one mechanic every lever routes through."
**Context:** Design discussion on 2026-08-30 about a "regional allies" / "allied mode" gameplay axis (captured in `design/allied-mode-proposal.md`).
**Implication:** Any feature that gives "Others" agency should manipulate the `pop` object directly at phase boundaries (scripted environmental resistance), never add `game.players.others`. A literal third player means rewriting `gainAt` to be 3-way, auditing every `['p1','p2']` loop, driving a third agent through `aiStep` under the human-fair-pacing rule, and fixing `simulate.js`/`balance-sim.js` — wide blast radius through the most rounding-sensitive code in the project. The scripted approach doesn't foreclose a real third player later if a 3-way FFA mode is ever wanted.

## 2026-08-29 — Only `generateStartingPosition` consumes replay-relevant RNG; every action function is deterministic
**Finding:** Before building the action-log replay, grepped the whole authoritative path (`mobile/engine.js` + `mobile/game.js`) for `rng` / `Math.random` / `Date` / `performance`. The only RNG draws that matter for reproduction are at game creation: `E.generateStartingPosition()` (the opening map) plus AI setup (`pickAIProfile`, `aiTargetGroup`). During play, only `pickAIRallyTarget` calls `game.rng()`. All six player-action functions (`investCash`, `playRallyToken`, `craftToken`, `tapAgenda`, `activatePower`, `activateNationwideRally`) and `endPhase`/`startPhase`/`applyPayouts`/`finalizeGame` are fully deterministic — no randomness, no wall-clock. Because replay re-applies the recorded *primitive calls* (not `aiStep`), the AI's own RNG never runs during replay, so a single seeded PRNG passed to `createGame` reproduces the entire game. Confirmed across 5 full politician-pair games (hundreds of interleaved human+AI actions each) replaying to byte-identical final seats and composite score.
**Context:** Systematic grep of the engine/game layer during the v2.2.0 action-log implementation, then verified by the new `assertReplayMatches` guard in `mobile/simulate.js`.
**Implication:** Input-based replay is low-risk in this codebase specifically because the action layer is already pure. Any future edit that adds `Math.random()`, `Date.now()`, or other non-determinism into an action function (or `endPhase`) silently breaks replay — and, later, multiplayer sync and server-side leaderboard validation. `npm test`'s `assertReplayMatches` catches it; keep that guard.

## 2026-08-29 — `click` can't fire until the finger lifts, and Playwright structurally cannot measure it
**Finding:** A user report that double-tapping a state to invest "feels laggy even if they don't appear laggy" — an exactly correct description, because the sound and FX were fast once they started, they just started late. All 34 interaction handlers in `mobile/main.js` were bound to `click`, which cannot fire until `touchend`. A real finger dwells on the glass for ~70–120 ms, and every one of those milliseconds lands before the handler runs. Captured event order in WebKit: `pointerdown+0 → touchstart+0 → pointerup+0 → touchend+0 → click+7ms`. That 7 ms is a *synthetic* tap — Playwright presses and releases in the same tick, so the harness can never reproduce the dwell that is the entire quantity being removed. Fixed with a `fastTap()` helper that binds `pointerdown` and keeps a `click` fallback (deduped on a 700 ms window) so keyboard activation still works on real `<button>`s. Two smaller contributors on the same path: `.fx-flash` animated `width`/`height`/`margin` (layout properties, so 450 ms of main-thread layout+paint per tap, precisely while tapping fast), and `investPaid()` spawned the visual FX *after* `renderAll()` even though the sound had already been moved ahead of it for exactly this reason.
**Context:** Found while investigating the user's report after a v2.1.0 performance pass. The engine benchmark had already ruled out game logic (all hot paths in the µs range) and the in-game tap measured 3 ms median / 7 ms max, so the lag had to be upstream of the handler.
**Implication:** Bind game actions to `pointerdown`, not `click` — but never the politician carousel or any scrollable surface, where the `click` binding is what stops a swipe from firing a card. More generally: a clean automated-test pass is not evidence about perceived input latency, because synthetic taps have zero dwell. This class of change needs a real thumb on real glass.

## 2026-08-29 — A `loading="lazy"` image in a hidden subtree never loads, so the welcome gate was a pure 3.5 s stall
**Finding:** The welcome screen held "Begin Campaign" disabled until three carousel portraits settled, with a `setTimeout(resolve, 3500)` as a safety net. ## 2026-08-29 — Portraits were alpha-free RGB PNG; gzip cannot compress PNG, and coordinate rounding cannot fix a traced SVG
**Finding:** All 21 politician portraits were 8-bit **RGB** PNG — colour type 2 in the IHDR, i.e. no alpha channel — a lossless codec carrying photographic art. Because PNG is already deflated, GitHub Pages' `content-encoding: gzip` does nothing for it, so 19.75 MB was real wire traffic on every cold visit. Re-encoding the identical 768 px pixels as WebP q80 gave **19.75 MB → 2.05 MB (9.4×)**; JPEG q82 gave 2.87 MB. Separately, two party-logo SVGs were the same failure in vector form: `All_India_Trinamool_Congress_logo_(3).svg` was 895 KB — 130,474 coordinate points across 7 auto-traced paths — rendering as a ~30 px badge. Rounding its coordinates to 2 decimal places saved only 13%; rasterising to 96 px WebP took it to 17 KB (989 KB → 25 KB for the pair). Deployed assets went 23 MB → 2.5 MB, boot payload 3.67 MB → 0.89 MB.
**Context:** Found during a full performance audit by reading the PNG IHDR colour-type byte directly and by counting coordinate floats in the SVG path data, rather than trusting file extensions.
**Implication:** Check an asset's colour type as well as its dimensions — no alpha means it should never be a PNG. And an auto-traced SVG is a raster problem wearing a vector extension: rasterise it, don't minify it. Note the earlier 2026-08-29 finding below fixed only the *dimensions* half of this; format was still wrong.

## 2026-08-29 — A DOM node on the `game` object silently kills the AI for the rest of the match

## 2026-08-29 — Rally dots go stale on *any* layout change, because several paths bypass `renderAll()`

## 2026-08-29 — "Missing" politician images were oversized PNGs blowing iOS Safari's image-memory cap
**Finding:** A user report that "most politician images are missing" in the latest deploy. ## 2026-08-28 — Viewport migration (v2.0.0): what old WebKit (~2014 iPad) does and doesn't support
**Finding:** The user's ~2014 iPad runs an old WebKit that silently drops several CSS features the v2.0.0 rework used: `margin-inline` / `margin-block` (Safari 14.5+), `clamp()` (13.4+), `visualViewport` (13+), flex `gap` (14.1+), `aspect-ratio` (15+). With `margin-inline:auto` dropped, the capped 520px column never centred — it pinned to the top-left corner. Separately confirmed: old WebKit does **not** re-resolve `margin:auto` after `max-width` clamps the width of a `position:fixed` element (the "apply the rules again with computed width" step of CSS 2.1 §10.3.7) — so even `margin-left/right:auto` left the box in the corner. The working fix was `left:50%` + `transform:translate(-50%,-50%)` (plain transform math, iOS 9+), in a rule placed at the very end of the stylesheet.
**Context:** User tested v2.0.0 on a ~2014 iPad (standalone/Home-Screen), reported "everything bunched up in the corner." An on-screen debug readout (temporarily added) showed `window.innerWidth` 768 but `document.documentElement.clientWidth` 168, `visualViewport` returning 0/0, and `rootFS 16px` (the `clamp()` fallback). A modern iPad and iPhone rendered correctly in Playwright/WebKit sim throughout — the sim uses current WebKit and can't reproduce the old-engine gaps.
**Implication:** For this project's CSS, centring a capped-width fixed layer must use `left/top:50% + transform`, never `inset:0 + margin:auto`. A ~2014 iPad is out of scope (would need every flex `gap` replaced with margins and `.action-btn` given an explicit height) — a current iPad is fine. Any future "looks broken only on an old device" report: add a temp on-screen readout of `innerWidth` / `documentElement.clientWidth` / `visualViewport.scale` / `getComputedStyle(:root).fontSize` rather than guessing.

## 2026-08-25 — iOS Safari auto-suspends AudioContext more aggressively for a bookmarked tab than a standalone PWA, and un-awaited resume() silently breaks the success/fallback contract

## 2026-07-28 — Starting-position seat variance: the stopping-rule threshold controls the mean without widening the spread
**Finding:** `mobile/engine.js`'s `generateStartingPosition()` (pre-fix) produced starting national seats averaging ~135-142 with a right tail reaching 180-200+ for one player — confirmed via 3,000-8,000-sample direct simulation, with ~46-47.5% of games putting at least one player over 150 seats (not a rare tail, close to a coin flip). Raising the advantage-draw stopping threshold (`drawStopAt`/`drawBudget`, 100/130 → 124/154) shifted the mean up to ~150 while leaving the standard deviation essentially unchanged (~12.4-12.7 across the whole tested range) — because the stopping rule is self-correcting: a player who draws a run of small states just needs more draws to cross the threshold, which keeps the overshoot (and therefore σ) stable regardless of where the threshold sits.
**Context:** User reported seeing 180-200-seat starts in actual play and initially proposed narrowing the baseline population range (500-2900 bps) as a fix; a parameter sweep showed narrowing the baseline instead just drags the average down without independently controlling the tail. **Implication:** Any future tuning of this generator should be checked via direct mean/σ simulation, not intuition about which knob "should" raise or lower the total or its spread — several knobs (`baseHi`, `drawStopAt`, `advHi`) all move the mean, but only empirical measurement revealed which one leaves σ untouched.

## 2026-07-23 — Seat-conversion rounding (state seats = round(popularity% × seats)) can over-allocate a state's total seats
**Finding:** Computing each player's seat share independently via plain rounding has no reconciliation step, unlike bps popularity redistribution (which guarantees the three shares always sum exactly). Worst case demonstrated: a 3-seat state at P1 50% / P2 25% / Others 25% gives exact quotas of 1.5 / 0.75 / 0.75 — independent rounding gives 2 / 1 / 1, handing out 4 seats from a state that only has 3.
**Context:** Found during a requested structural review of `design/economy-status-map.md`, by analogy to the redistribution engine's own "round one side, derive the other" discipline — the seat-conversion step never got the same treatment.
**Implication:** Fixed by switching to largest-remainder apportionment (Hamilton's method): give each side `floor(quota)` first, then hand out the state's leftover seats one at a time to whoever has the largest fractional remainder. Now documented with pseudocode and a worked example in the Core loop section. Should be re-validated against the plausibility-check seat totals once implemented, since it can shift exact seat counts in edge cases (though not the shape of the ~19-seat passive-opponent margin finding).
